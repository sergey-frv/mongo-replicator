# mongo-replicator

Односторонняя репликация MongoDB через change streams.

Назначение: миграция базы между кластерами MongoDB (в том числе одной версии) — дамп заливается на цель, затем репликатор непрерывно догоняет её до источника, пока не придёт время переключиться. Нужны только права на чтение базы источника и на запись в базу цели: прав на весь кластер, как у `mongosync` или при чтении oplog, не требуется.

Реплицируется одна база источника (`--db`): поток уровня базы, на источнике достаточно прав на чтение этой базы. На цели база может называться иначе (`--dst-db`). Несколько баз — несколько процессов, по одному на базу, в том числе в один целевой кластер (см. [«Несколько процессов»](#несколько-процессов)).

Переносятся DML (`insert`, `update`, `replace`, `delete`) и DDL `create`, `rename`, `createIndexes`, `dropIndexes`. Удаления (`drop` коллекции, `dropDatabase`) не применяются, а останавливают репликатор — решает оператор (см. [«Удаления»](#удаления)).

## Требования

- источник: replica set, MongoDB 6.0+ (нужен `showExpandedEvents` для DDL);
- цель: replica set, MongoDB 8.0; в базу `--dst-db` пишет только репликатор (в ней же — его служебная коллекция `_replicator_checkpoint`, см. [«Чекпойнт»](#чекпойнт)); другие базы целевого кластера могут использоваться, в том числе другими процессами репликатора;
- на цели уже восстановлен полный дамп источника, а `--start-ts` указывает на момент **до** начала этого дампа и ещё попадает в окно oplog источника;
- права на источнике и цели — см. [«Права»](#права);
- сборка: Go 1.26 (`make build` также выполняет `go mod tidy` и `go mod vendor`); тесты, линтер и `make run` — Docker с compose.

## Запуск

```sh
make build    # bin/mongo-replicator, ревизия из git describe
```

| Опция | Env | По умолчанию | |
|---|---|---|---|
| `--src` | `SRC_URI` | обязательна | URI источника; без пароля в URI пароль запрашивается в терминале (см. [«Пароли»](#пароли)) |
| `--dst` | `DST_URI` | обязательна | URI цели; пароль — так же, как для `--src` |
| `--start-ts` | `START_TS` | `0` | unix-сек, с которых читать поток при отсутствии чекпойнта |
| `--batch` | `BATCH_SIZE` | `1000` | максимум операций в одной пачке записи, `>= 1` |
| `--db` | `DB` | обязательна | база источника (поток уровня базы) |
| `--dst-db` | `DST_DB` | как `--db` | база на цели, куда пишется всё: DML, DDL, обе стороны rename |
| `--apply-drop` | `APPLY_DROP` | — | разрешить `drop` коллекции источника `<db>.<коллекция>` (см. [«После остановки на drop»](#после-остановки-на-drop)); флаг можно повторять, в env — через запятую; флаг заменяет `APPLY_DROP`, а не дополняет |
| `--log-level` | `LOG_LEVEL` | `info` | уровень лога в консоли (stdout): `debug`, `info`, `warn`, `error` (см. [«Логи»](#логи)) |
| `--log-file` | `LOG_FILE` | — | путь к файлу лога: JSON, дозапись; каталог должен существовать |
| `--log-file-level` | `LOG_FILE_LEVEL` | `info` | уровень лога в файле, те же значения; только вместе с `--log-file` |
| `--progress` | `PROGRESS` | `auto` | `tty` — панель статуса в терминале, `plain` — построчный лог, `auto` — панель, если stdout — терминал (см. [«Панель статуса»](#панель-статуса)) |
| `--no-clear` | `NO_CLEAR` | — | не очищать экран перед панелью статуса; по умолчанию экран очищается до строк запуска, и они остаются видны над панелью; в режиме `plain` не действует; с `--progress tty` при перенаправленном stdout последовательность очистки попадёт в файл вместе с остальными последовательностями панели |
| `--state-dir` | `STATE_DIR` | `$XDG_STATE_HOME/mongo-replicator` или `~/.local/state/mongo-replicator` | каталог файлов состояния на машине: накопленный трафик процессов и сводка по ним (см. [«Состояние на машине»](#состояние-на-машине)) |

Без `--db` или с пустым `DB=` — выход с кодом `2`. Уровни лога принимаются только в нижнем регистре и только из списка (`INFO`, `1`, `trace` — выход с кодом `2`); пустые `LOG_LEVEL=` и `LOG_FILE_LEVEL=` — тоже ошибка, пустой `LOG_FILE=` — файла нет. `--log-file-level` без `--log-file` — выход с кодом `2`; `--progress` — только `auto`, `tty`, `plain` (пустое `PROGRESS=` — тоже ошибка, код `2`); `NO_CLEAR` — `true`/`1` или `false`/`0`, пустое `NO_CLEAR=` — включено, другое значение (`yes`) — выход с кодом `2`, а заданный в env `NO_CLEAR=true` из командной строки не снять (`--no-clear=false` — ошибка, код `2`); ошибка открытия файла лога (нет каталога, нет прав) и ошибка создания каталога `--state-dir` — тоже. Имена `--db` и `--dst-db` проверяются по правилам MongoDB (без `/\. "$` и NUL, не длиннее 63 байт); служебные базы (`admin`, `config`, `local`, в любом регистре) указать нельзя. Элементы `--apply-drop` — namespace базы `--db` (`<db>.<коллекция>`, коллекция непустая, имя разбивается по первой точке: `db.a.b` — коллекция `a.b`); пробелы вокруг срезаются, пустой `APPLY_DROP=` — пустой список.

Опции принимаются только с двумя дефисами: `--src`, а не `-src`, как было в первой версии (`-src` разбирается как набор коротких флагов `-s -r -c`).

```sh
./bin/mongo-replicator \
    --src "mongodb://repl@src1:27017,src2:27017/?replicaSet=rs8&authSource=admin" \
    --dst "mongodb://repl@dst1:27017,dst2:27017/?replicaSet=rsdst&authSource=admin" \
    --db urlshrinker \
    --start-ts 1791900000
```

Пароля в URI нет — при старте он будет запрошен в терминале, отдельно для источника и цели (см. [«Пароли»](#пароли)).

Типичный запуск — вручную в `tmux` на часы и дни: в консоли панель статуса и предупреждения над ней, полный JSON-лог — в файле (см. [«Панель статуса»](#панель-статуса), [«Логи»](#логи)):

```sh
./bin/mongo-replicator --src "$SRC_URI" --dst "$DST_URI" --db urlshrinker \
    --log-file /var/log/repl/urlshrinker.log
```

### `--dst-db`

База на цели называется иначе (`urlshrinker` → `urlshrinker_v2`), в том числе копия рядом с оригиналом на том же целевом кластере:

```sh
./bin/mongo-replicator --src "$SRC_URI" --dst "$DST_URI" \
    --db urlshrinker --dst-db urlshrinker_v2 --start-ts 1791900000
```

Дамп на цель заливается сразу под новым именем:

```sh
mongorestore --uri "$DST_URI" --nsFrom 'urlshrinker.*' --nsTo 'urlshrinker_v2.*' dump/
```

На цели пишется только в `--dst-db`, база с именем источника там не появляется. Чекпойнт — свой у каждой базы цели (в её коллекции `_replicator_checkpoint`), поэтому две копии одной базы на одном целевом кластере (`--dst-db urlshrinker_v2` и `--dst-db urlshrinker_v3`) реплицируются двумя процессами одновременно (см. [«Несколько процессов»](#несколько-процессов)).

URI удобно держать в `cmd/mongo-replicator/.env` (он в `.gitignore`):

```sh
# cmd/mongo-replicator/.env
SRC_URI='mongodb://repl@src1:27017/?replicaSet=rs8&authSource=admin'
DST_URI='mongodb://repl@dst1:27017/?replicaSet=rsdst&authSource=admin'
DB=urlshrinker
```

URI в `.env` — в одинарных кавычках: без них `&` при `. .env` шелл примет за запуск в фоне, и `SRC_URI` останется пустым.

```sh
set -a; . cmd/mongo-replicator/.env; set +a
./bin/mongo-replicator --start-ts 1791900000
```

`--start-ts` нужен только на первом запуске: дальше поток продолжается с чекпойнта на цели, а опция игнорируется.

### Чекпойнт

Чекпойнт хранится на цели в самой базе цели — в служебной коллекции `<dst-db>._replicator_checkpoint`, один документ `_id: "checkpoint"`. Отдельной базы для чекпойнтов нет: на цели достаточно прав на одну базу, а чекпойнт живёт и удаляется вместе с данными. Посмотреть:

```js
db.getSiblingDB("urlshrinker_v2")._replicator_checkpoint.findOne({}, {token: 0})   // --dst-db
```

| Поле | |
|---|---|
| `db`, `dst_db` | пара баз, для которой записан чекпойнт: `--db` и `--dst-db` |
| `token` | resume token потока — применённая позиция |
| `clusterTime`, `updatedAt` | время применённой позиции (время кластера источника) и время её сохранения |
| `owner`, `lease_until` | аренда: есть, пока процесс работает (или пока не истекла аренда упавшего), см. [«Несколько процессов»](#несколько-процессов) |

Чекпойнт помнит базу источника, для которой записан. Сменить `--db` поверх существующего чекпойнта нельзя — выход с кодом `1` (`ErrDBMismatch`, см. [«Восстановление»](#восстановление)). Другая `--dst-db` — другая база с другим чекпойнтом: без `--start-ts` это выход с кодом `1` (`чекпойнта нет и start-ts не задан`).

Служебная коллекция создаётся сама при захвате аренды на старте. Поэтому опечатка в `--dst-db` оставляет на цели пустую базу с этим именем и пустой `_replicator_checkpoint`: документ без позиции процесс при выходе удаляет, а коллекцию и базу — нет. Удалите её вручную (`db.getSiblingDB("<опечатка>").dropDatabase()`).

Удалить служебную коллекцию у работающего процесса — значит потерять позицию: процесс выйдет с кодом `1` (`ErrLeaseLost`) на следующем продлении аренды или сохранении чекпойнта, а рестарт без `--start-ts` — с `чекпойнта нет и start-ts не задан`.

**Новая полная заливка** (например, после выхода с кодом `1` из-за выпадения из oplog): остановите процесс этой базы и удалите чекпойнт — служебную коллекцию или всю базу цели, — затем залейте дамп и запустите с новым `--start-ts`:

```js
db.getSiblingDB("urlshrinker_v2")._replicator_checkpoint.drop()   // или db.getSiblingDB("urlshrinker_v2").dropDatabase()
```

`mongorestore --drop` служебную коллекцию не удаляет: её нет в дампе источника. Накопленный трафик хранится не в чекпойнте, а в файле на машине, и удаление чекпойнта или базы его не сбрасывает (см. [«Состояние на машине»](#состояние-на-машине)).

**Дамп и резервные копии.** Служебная коллекция может оказаться в базе источника: например, источник раньше сам был целью репликации в обратную сторону. Дамп для начальной заливки снимайте без неё:

```sh
mongodump --uri "$SRC_URI" --db urlshrinker --excludeCollection _replicator_checkpoint --out dump/
```

или исключите её при восстановлении (`mongorestore --nsExclude 'urlshrinker._replicator_checkpoint'`). Иначе на цель попадёт чужой чекпойнт: при совпадении имён баз репликатор примет его за свой и проигнорирует `--start-ts`. Дальше — как повезёт с токеном: либо выход с кодом `1` с вводящей в заблуждение ошибкой «точка возобновления выпала из oplog источника», либо (токен простоя, сохранённый без событий) поток **молча** стартует со времени чужого токена — если оно позже начала дампа, события между ними пропускаются и цель расходится с источником без ошибки. Перед первым запуском убедитесь, что на цели чекпойнта нет: `db.getSiblingDB("urlshrinker")._replicator_checkpoint.countDocuments()` — `0`. То же исключение — для резервных копий базы цели, если из них будут заливать другую цель.

Записи в `_replicator_checkpoint` на источнике в поток не попадают: поток всегда отсекает служебную коллекцию. Переименование на источнике коллекции **в** служебное имя или **из** него — перманентная ошибка: выход с кодом `1` (`ErrReservedCollection`, `rename в служебную коллекцию _replicator_checkpoint или из неё`). Чекпойнт стоит перед этим событием, рестарт снова упрётся в него: переименуйте коллекцию на источнике в другое имя и сделайте новую полную заливку.

### Пароли

Имя пользователя указывается в URI, пароль — нет. Если в URI есть пользователь, но нет пароля (`mongodb://repl@host/...`, пустой `repl:@host` — то же самое), он запрашивается в терминале без эха: `Пароль repl@src1:27017 (источник): `, затем так же для цели. Запросы независимые: даже при одинаковом пользователе на обоих кластерах пароль спрашивается дважды. Оба запроса — сразу при старте, до подключения, и только после разбора обоих URI: ошибка в `--dst` видна до ввода пароля источника. Пустой ввод или Ctrl+D — выход с кодом `2`, Ctrl+C — выход с кодом `130`, эхо терминала при этом восстанавливается.

URI без пользователя (локальный compose, `make run`) и `authMechanism=MONGODB-X509` / `MONGODB-OIDC` пароля не требуют — запроса нет.

Запрос возможен, только если и stdin, и stderr — терминал (приглашение пишется в stderr): с `2>log` пароль не спрашивается. Запуск без терминала (`nohup`, будущий сервис): передайте URI **с паролем** через окружение — оно не видно в `ps` и не попадает в историю шелла:

```sh
read -rs SRC_URI && export SRC_URI   # вставить mongodb://repl:секрет@src1:27017/?replicaSet=rs8&authSource=admin
read -rs DST_URI && export DST_URI
nohup ./bin/mongo-replicator --db urlshrinker --log-file /var/log/repl/urlshrinker.log \
    >/dev/null 2>>replicator.stderr &
```

stdout не нужен — JSON уже пишется в файл. stderr сохраняется отдельно: туда идут ошибки опций и открытия файла лога, подсказка про пароль без терминала, ошибки записи лога и паника.

Или `.env` с URI с паролем (в одинарных кавычках) и правами `0600` (`chmod 600 cmd/mongo-replicator/.env`). `export SRC_URI=mongodb://repl:секрет@...` прямо в командной строке пароль в историю шелла пишет — используйте `read -rs`. Без терминала и без пароля в URI — выход с кодом `2` с подсказкой про `SRC_URI`/`DST_URI`.

URI с паролем во флаге `--src`/`--dst` работает, но в лог пишется WARN `пароль передан в --src/--dst` (поле `cluster`): командная строка остаётся в истории шелла и видна всем пользователям машины в `ps`. URI с паролем из `SRC_URI`/`DST_URI` — без WARN.

`authMechanism=SCRAM-SHA-1`/`SCRAM-SHA-256` в URI без пароля не поддерживается: драйвер отвергает такой URI до запроса пароля, выход с кодом `2` с подсказкой. Уберите `authMechanism` — механизм по умолчанию сам выберет SCRAM. Для `PLAIN` (LDAP) и `MONGODB-AWS` пароль в терминале не запрашивается: передайте URI с паролем через `SRC_URI`/`DST_URI`. `GSSAPI` (Kerberos) не поддерживается: драйвер собран без тега `gssapi`.

Неверный пароль — выход с кодом `1` при подключении, в логе ERROR `не удалось подключиться` с `hint: проверьте пользователя и пароль`.

### Права

| Источник | Цель |
|---|---|
| `read` на `--db` (`find` + `changeStream`) | `readWrite` на `--dst-db` |

`readWrite` включает всё нужное на цели: запись, DDL, `listCollections` (проверка перед `drop`) и `drop` коллекции по `--apply-drop`. Право `dropDatabase` не нужно: `dropDatabase` не применяется.

Чекпойнт и аренда процесса — в коллекции `_replicator_checkpoint` самой базы цели (см. [«Чекпойнт»](#чекпойнт)), поэтому других прав на цели не нужно: каждому процессу — `readWrite` на свою `--dst-db`. Коллекцию заранее создавать не нужно: она и документ чекпойнта создаются автоматически при захвате аренды на старте.

### Проверка перед запуском

В mongosh под пользователем репликатора. `mongosh "$SRC_URI"` с URI без пароля сам спросит пароль.

Источник — поток по базе открывается (`null` без ошибки — права есть, код 13 — нет):

```js
const cs = db.getSiblingDB("urlshrinker").watch([], {showExpandedEvents: true});
cs.tryNext();
cs.close();
```

Источник — `--start-ts` ещё в окне oplog (`null` без ошибки — в окне, код 286 `ChangeStreamHistoryLost` — выпал, нужна более свежая заливка):

```js
const cs = db.getSiblingDB("urlshrinker").watch([], {startAtOperationTime: Timestamp({t: 1791900000, i: 0})});
cs.tryNext();
cs.close();
```

Цель — запись в базу цели (`--dst-db`) с `w: "majority"`:

```js
const d = db.getSiblingDB("urlshrinker_v2");
d.replicator_probe.insertOne({_id: 1}, {writeConcern: {w: "majority"}});
d.replicator_probe.drop();
```

### Локальная проверка

```sh
make docker-volumes   # один раз: тома go-build-cache и go-lint-cache
make run              # mongo-src (8.0, rs8) + mongo-dst (8.0, rsdst) и репликатор с --db test и --start-ts = сейчас (поднимается и toxiproxy — для тестов, не используется)
```

Запуск против локальных mongo — только через `make run`: в rs-конфиге члены записаны как `mongo-src`/`mongo-dst`, с хоста эти имена не резолвятся.

`make run` идёт в терминале, поэтому показывает [панель статуса](#панель-статуса): `--log-level debug` из `Makefile` в консоли не действует (над панелью — только WARN и выше), и при старте печатается WARN `полный лог не пишется: добавьте --log-file`. Для построчного DEBUG-лога добавьте `--progress plain` к команде цели `run` в `Makefile`.

`make test-integration` удаляет только базы `it_*`: чекпойнт базы `test` от `make run` (`test._replicator_checkpoint` на `mongo-dst`) остаётся, и следующий `make run` продолжит с него. Чтобы начать с чистого листа — `make down`. Каталог состояния `make run` — внутри контейнера, который удаляется после выхода: накопленный трафик каждый запуск начинается с нуля.

### Разработка

Пакеты модуля `github.com/sergey-frv/mongo-replicator`:

```
cmd/mongo-replicator/   CLI: опции, учётные данные и запрос пароля, лог, маскирование секретов, подсказки, запуск
cmd/panel-demo/         демо панели статуса на мок-данных, без кластеров
internal/replicator/    ядро: поток изменений, запись на цель, DDL, чекпойнт, аренда, статус
internal/statefile/     файл состояния на машине: путь, чтение и запись, сводка
internal/traffic/       счётчики трафика клиентов
internal/panel/         панель статуса в терминале
```

```sh
make test               # юнит-тесты, mongo не нужна
make test-integration   # интеграционные тесты против mongo-src и mongo-dst (и через toxiproxy), строго последовательно (-p 1): тесты делят кластеры, а тесты аренды чувствительны ко времени
make lint               # golangci-lint
make panel-demo         # bin/mongo-replicator-panel — демо панели статуса (см. «Панель статуса»)
make down               # остановить контейнеры и удалить их тома
```

Интеграционные тесты берут кластеры из `IT_SRC_URI`/`IT_DST_URI` (заданы только в сервисе `app` в `docker-compose.yml`) и удаляют базы `it_*` на обоих кластерах (на цели — вместе с их чекпойнтами). Отдельные переменные нужны, чтобы тесты не ушли на рабочие кластеры из `SRC_URI`/`DST_URI` загруженного `.env`. Запускайте их через `make test-integration`.

Сетевые тесты (`TestIntegrationNet*`) идут к кластерам через [Toxiproxy](https://github.com/Shopify/toxiproxy): обрыв связи с источником и с целью, «зависание» (соединение есть, ответов нет), удержание аренды при зависшей цели, учёт трафика после обрыва. `make test-integration` поднимает сервис `toxiproxy` сам: прокси `src` (`toxiproxy:27001` → `mongo-src`) и `dst` (`toxiproxy:27002` → `mongo-dst`) создаются в начале прогона через API (`IT_PROXY_API`), тесты подключаются по `IT_SRC_PROXY_URI`/`IT_DST_PROXY_URI` с `directConnection=true` — без него драйвер найдёт узлы по адресам из конфигурации replica set и пойдёт мимо прокси. Без `IT_PROXY_API` сетевые тесты пропускаются. Версия Toxiproxy — 2.12.0: 2.13.0 требует Go 1.27.

## Несколько процессов

Одна база — один процесс. Несколько баз реплицируются в один целевой кластер параллельно — по процессу на базу (`--db`, `--dst-db`), каждый со своим чекпойнтом в своей базе цели, своим файлом состояния и своим файлом лога, например в отдельных окнах `tmux`:

```sh
./bin/mongo-replicator --db urlshrinker --log-file /var/log/repl/urlshrinker.log
./bin/mongo-replicator --db billing --log-file /var/log/repl/billing.log
```

Документ чекпойнта в базе цели — одновременно **аренда**: при старте процесс записывает в него себя (`owner` — `hostname:pid:<8 случайных hex>`) и срок `lease_until` — время сервера цели + 60 с, затем продлевает аренду каждые 10 с. Продление идёт в своей горутине: долгая операция (сборка индекса `createIndexes` на большой коллекции) его не задерживает. Срок считается по часам сервера цели, часы машин с репликаторами не участвуют. При выходе (SIGINT/SIGTERM, перманентная ошибка) аренда снимается сразу; по `SIGQUIT` (Ctrl+\\ в панели, `kill -QUIT`) и `kill -9` не снимается — база цели освободится по её истечении; не удалось — WARN `аренда не снята: база цели освободится по её истечении`.

- **Второй процесс на ту же базу цели** не стартует: выход с кодом `1`, ERROR `аренда базы цели занята: базу <dst-db> уже реплицирует <owner>, аренда до <время>` (`ErrLeaseHeld`). Если тот процесс упал (`kill -9`, OOM, падение машины) — аренда истечёт сама, новый процесс стартует не позже чем через 60 с.
- **Аренду забрали** — процесс не продлевал её дольше срока (например, машина стояла на паузе) и базу захватил другой: при следующем продлении или сохранении чекпойнта выход с кодом `1`, ERROR `аренда базы цели потеряна` (`ErrLeaseLost`). Проверьте, не запущены ли два репликатора на одну базу.
- **Потеря связи с целью**: продление повторяется каждые 10 с (WARN `продление аренды не удалось, повтор`); если успешного продления нет дольше 40 с (2/3 срока), процесс сам прекращает запись и уходит в обычный повтор (WARN `ошибка репликации, повтор`: `аренда не продлевается и скоро истечёт`) — раньше, чем аренда истечёт и её сможет захватить другой процесс. Когда связь восстановится, процесс захватит аренду заново и продолжит с чекпойнта. Тот же срок проверяется перед каждой записью на цель (пачка коллекции, DDL): процесс, простоявший дольше аренды (`SIGSTOP`, миграция ВМ) до этой проверки, не пишет на цель поверх процесса, успевшего её захватить.

Остаточный риск: аренду проверяет процесс, а не сервер цели при записи, поэтому одна запоздавшая операция возможна. Уже отправленная на сервер операция (например, пачка записи) может выполниться и после остановки процесса на клиенте; процесс, приостановленный дольше срока аренды между проверкой и отправкой, после возобновления отправит одну операцию, прежде чем заметит потерю аренды. Аренда не даёт двум процессам работать одновременно, но такую запоздавшую запись не отменяет. Не приостанавливайте репликатор дольше чем на 40 с — останавливайте его.

Чекпойнты всех баз целевого кластера — на цели, под пользователем с правами на все эти базы:

```js
db.adminCommand({listDatabases: 1, nameOnly: true}).databases.forEach(d => {
    const c = db.getSiblingDB(d.name)._replicator_checkpoint.findOne({}, {token: 0});
    if (c) printjson(c);
});
```

Поля — см. [«Чекпойнт»](#чекпойнт); работает сейчас — `lease_until` в будущем. Документ без `token` — процесс запущен, но ещё не сохранил позицию; с `lease_until` в прошлом — процесс упал до первого сохранения: документ остаётся до следующего запуска на эту базу (или удалите его вручную). Процессы одной машины и их трафик видны и без цели — в файлах состояния (см. [«Состояние на машине»](#состояние-на-машине)).

## Гарантии

- at-least-once: после сбоя поток продолжается с последнего сохранённого resume token, события после него читаются повторно;
- операции идемпотентны: insert/update/replace применяются как replace-upsert полного документа по `_id`, delete — по `_id`; повторное применение даёт то же итоговое состояние. DDL «уже есть» / «уже нет» при повторе игнорируется;
- чекпойнт хранится на цели (`<dst-db>._replicator_checkpoint`) и двигается только после успешной записи данных; клиент цели работает с `w:majority`, чтобы чекпойнт не обогнал данные при failover, а сам чекпойнт читается только с primary, даже если в `--dst` задан `readPreference` (устаревший токен с отстающей secondary повторил бы rename поверх применённого состояния);
- после DDL чекпойнт сохраняется сразу, чтобы rename/drop не повторялись после рестарта; при остановке на `drop`/`dropDatabase` всё до удаления уже на цели, а чекпойнт стоит перед удалением;
- любая ошибка, кроме перманентных (см. коды выхода), — повтор через 5 с без выхода. Так переживаются сеть и failover, но так же бесконечно повторяются и постоянные ошибки (цель не приняла документ или DDL): чекпойнт стоит перед проблемным событием, в логе каждые 5 с WARN `ошибка репликации, повтор`. После исправления цели репликация продолжается сама;
- зависшая сеть к источнику (соединение есть, ответов нет) замечается не сразу: драйвер признаёт узел недоступным после таймаутов heartbeat — с умолчаниями (`connectTimeoutMS` 30 с, `heartbeatFrequencyMS` 10 с) по оценке до ~80 с (в тестах с `connectTimeoutMS=2000&heartbeatFrequencyMS=500` — ~6 с). До этого нет ни WARN `ошибка репликации, повтор`, ни `прогресс`. Быстрее — меньшие `connectTimeoutMS`/`heartbeatFrequencyMS` в URI `--src`. Зависшая цель ограничена арендой: самоостановка через 40 с (см. [«Несколько процессов»](#несколько-процессов)).

Лог пишется в консоль и, с `--log-file`, в файл (см. [«Логи»](#логи)); в терминале консоль по умолчанию заменяет панель статуса (см. [«Панель статуса»](#панель-статуса)). Раз в 10 с — INFO `прогресс` (см. [«Мониторинг лага»](#мониторинг-лага)), раз в минуту — INFO `трафик на машине`, при выходе — INFO `трафик` (см. [«Трафик»](#трафик)); применённый DDL — INFO `DDL применён` (`op`, `ns`, `to` — namespace источника; при `--dst-db` ещё `dst` — `ns` на цели, для rename новая коллекция на цели — `<dst-db>.<коллекция из to>`), `drop` по `--apply-drop` — INFO `drop применён по --apply-drop`; пропущенные события — WARN, кроме `update`, документа которого на источнике к моменту чтения уже нет: он пропускается без записи в лог (см. [«Ограничения»](#ограничения), (a)).

Коды выхода:

| Код | Причина |
|---|---|
| `0` | остановка по SIGINT/SIGTERM (незаписанный хвост будет перечитан при следующем запуске); `--help` |
| `1` | точка возобновления выпала из oplog источника (нужна новая полная заливка цели); нет ни чекпойнта, ни `--start-ts`; чекпойнт базы цели записан для другой базы источника (`ErrDBMismatch`); базу цели уже реплицирует другой процесс (`ErrLeaseHeld`) или аренду забрали во время работы (`ErrLeaseLost`, см. [«Несколько процессов»](#несколько-процессов)); на источнике удалена коллекция, которая есть на цели, или база (`*DropError`, см. [«Удаления»](#удаления)); событие другой базы в потоке (`ErrForeignNamespace`, баг); на цели есть база с именем `--dst-db` в другом регистре (сервер отвергает запись, код 13297); поток закрыт событием `invalidate` (`ErrStreamInvalidated`); на источнике коллекция переименована в служебное имя `_replicator_checkpoint` или из него (`ErrReservedCollection`, см. [«Чекпойнт»](#чекпойнт)); событие изменения больше 16 МБ (код 10334, см. [«Ограничения»](#ограничения)); кластер недоступен (`Ping` за 10 с) или неверный пароль |
| `2` | ошибка опций, в т.ч. не задана `--db`, некорректное имя базы в `--db`/`--dst-db`, некорректный `--apply-drop`, некорректный уровень лога, некорректный `--progress` (в т.ч. пустой `PROGRESS=`), некорректный `NO_CLEAR`, `--log-file-level` без `--log-file`, не удалось открыть файл `--log-file` (нет каталога или прав), не удалось создать каталог `--state-dir`; некорректный URI (в т.ч. ошибка DNS для `mongodb+srv`), нет пароля и нет терминала, пустой ввод или Ctrl+D при запросе пароля — всё до подключения; дамп горутин по `SIGQUIT` (Ctrl+\\ в панели, `kill -QUIT`) — рантайм Go выходит сразу, аренда не снимается |
| `130` | Ctrl+C или SIGTERM во время запроса пароля |

Перманентные ошибки не повторяются: в лог пишется ERROR с подсказкой оператору, затем выход с кодом `1`.

### Восстановление

- **Выпадение из oplog** — новая полная заливка цели, удаление чекпойнта, запуск с новым `--start-ts` (см. [«Чекпойнт»](#чекпойнт)).
- **`ErrDBMismatch`** (`чекпойнт записан для другой пары баз`, в тексте — обе пары): чекпойнт базы `--dst-db` записан для другой базы источника. Если `--db` перепутана — запустите с прежней, чекпойнт подхватится. Если базу источника нужно сменить: остановите процесс, удалите `<dst-db>._replicator_checkpoint` (или всю базу цели, см. [«Чекпойнт»](#чекпойнт)), залейте нужную базу на цель заново и запустите с новыми опциями и новым `--start-ts` до начала дампа.
- **`ErrLeaseHeld`**, **`ErrLeaseLost`** — см. [«Несколько процессов»](#несколько-процессов).
- **Остановка на `drop` коллекции** — см. [«После остановки на drop»](#после-остановки-на-drop).
- **Остановка на `dropDatabase`** (`на источнике удалена база ...`): на цели данные остались, всё до удаления применено. Продолжить старый поток нельзя ни с какими опциями. Когда база на источнике создана заново: удалите чекпойнт, залейте базу на цель и запустите с новым `--start-ts`.
- **`ErrStreamInvalidated`** (`поток инвалидирован`): поток закрыт сервером; в штатном порядке событий до него не доходит — репликатор останавливается раньше, на `dropDatabase`. Восстановление — как после `dropDatabase`.
- **`ErrReservedCollection`** (`rename в служебную коллекцию _replicator_checkpoint или из неё`): переименуйте коллекцию на источнике в другое имя и сделайте новую полную заливку (см. [«Чекпойнт»](#чекпойнт)).

## Логи

Два приёмника с независимыми уровнями:

- **консоль** (stdout, `--log-level`): если stdout — терминал, цветной текст со временем, а при панели статуса — только WARN и выше над ней (см. [«Панель статуса»](#панель-статуса)); при перенаправлении (`>file`, `| jq`) — JSON;
- **файл** (`--log-file`, `--log-file-level`): всегда JSON, по строке на событие, дозапись (`O_APPEND`); файл создаётся с правами `0640`, каталог — нет.

Поля JSON: `m` — сообщение, `e` — ошибка, `l` — уровень, `t` — время (RFC3339), остальные — по событию.

При старте первой строкой пишется INFO `лог` с настройками приёмников — по ней в файле видна граница запусков. В терминале она выглядит так, в файле — та же строка JSON-ом:

```
2026-10-14T16:00:00+06:00 INF лог console=info/text file=/var/log/repl/urlshrinker.log file_level=info
```

Без `--log-file` — пустой `file` (в терминале `file=`, в JSON `"file":""`), без `file_level`. Строки уровня INFO при старте (`лог`, `revision`) попадают только в приёмники с уровнем `info` и ниже: при `--log-level warn` в консоли их нет.

Уровни раздельные: при разборе проблемы удобно оставить консоль на `info`, а DEBUG писать только в файл:

```sh
./bin/mongo-replicator --db urlshrinker \
    --log-file /var/log/repl/urlshrinker.log --log-file-level debug
```

Запись без буфера: при выходе по сигналу или ошибке ничего не теряется.

Ротация не встроена — внешний `logrotate` с `copytruncate`, например `/etc/logrotate.d/mongo-replicator`:

```
/var/log/repl/*.log {
    daily
    rotate 14
    compress
    delaycompress
    missingok
    notifempty
    copytruncate
}
```

`copytruncate` копирует файл и обрезает исходный, а репликатор продолжает писать в тот же дескриптор; благодаря `O_APPEND` запись идёт с начала обрезанного файла, без «дыры» из нулевых байтов. Строки, записанные между копированием и обрезкой, теряются — обычно это одна-две строки.

## Панель статуса

В терминале — панель, как у `docker build`: под строками запуска (экран перед ней очищается, см. ниже), обновляется раз в секунду; строки лога печатаются над ней и сдвигают её вниз:

```
● работает  urlshrinker → urlshrinker_v2   с запуска 25м0с
── репликация ──────────────────────────────────────────────────────
  лаг        0с             применено до 19:37:18
  скорость   19/с           ▏▆█▆██▆███▆█▆██▆▆█▆█▆▕ 5–25/с
  применено  1 727 851      пачка 19:37:18: 1 (ins 1) в PrivateUrls
  DDL        11:40:02       createIndexes urlshrinker.PublicUrls (slug_1)
── трафик ──────────────────────────────────────────────────────────
  источник   ↓ 4.1 KiB/с    ▏▆▆█▆▆▆█▆▆█▆▆▆█▆▆▆█▆▆▕ всего ↓ 881 MiB ↑ 2.7 MiB
  цель       ↑ 3.8 KiB/с    ▏▅▅█▅▅▅█▅▅█▅▅▅█▅▅▅█▅▅▕ всего ↑ 278 MiB ↓ 36.3 MiB
  машина     процессов 1, активно 1 · на 19:36  всего ↓ 881 MiB ↑ 277.9 MiB
```

Во время догона шапка — `◐ догоняет`, а в строке лага вместо «применено до» — полоса, доля пройденного и оценка, когда лаг дойдёт до нуля:

```
◐ догоняет  urlshrinker → urlshrinker_v2   с запуска 3м10с
── репликация ──────────────────────────────────────────────────────
  лаг        1д4ч           ███████████░░░░░░░░░ 58% · ~1м0с до 0
```

| Строка | |
|---|---|
| шапка | состояние, базы, время работы процесса. Состояние: `◌ запуск` (тусклым), `● работает` (зелёным), `◐ догоняет` (жёлтым — работает и идёт догон), `↻ повтор N` (жёлтым), `✗ остановлен` (с ошибкой — красным, иначе тусклым) |
| `лаг` | отставание от источника: до 10 с — зелёным, до минуты — жёлтым, дальше — красным; затем время применённой позиции. `неизвестен` — пока нет чекпойнта или не удался `ping` источника |
| `скорость` | операций в секунду за последний интервал `прогресс` (10 с), график за минуту и его диапазон; от 10/с — целые с разделителем тысяч (`12 000/с`), ниже — с одним знаком (`0.4/с`) |
| `применено` | операций с запуска; последняя пачка: время, число операций по видам (`ins`, `upd`, `rep`, `del`) и коллекции (до трёх, дальше — «и ещё N») |
| `DDL` | последнее DDL-событие (namespace источника), в том числе пропущенное (с пометкой); нет строки — DDL ещё не было |
| `источник`, `цель` | трафик процесса: скорость основного направления (источник ↓, цель ↑) за последнюю секунду, её график за минуту, всего получено ↓ и отправлено ↑ с начала процесса; `—` — замера ещё нет |
| `машина` | последняя сводка трафика по файлам состояния машины (раз в минуту): процессов (файлов), из них активных, время сводки, всего ↓ с источников и ↑ на цели; нет строки — сводки ещё не было (см. [«Состояние на машине»](#состояние-на-машине)) |
| `ошибка` | последняя ошибка (при повторе или остановке) — отдельной строкой красным |

Графики — за последнюю минуту, колонка — 3 секунды, высота столбика — относительно наибольшей из последних 5 колонок (15 с): после всплеска (догона) график сразу различим, а старые более высокие столбики упираются в верх; диапазон справа — настоящий за минуту. Скорость — голубым, источник — зелёным, цель — фиолетовым. Полоса догона появляется, когда лаг в работе доходит до минуты, и пропадает, когда он падает ниже 10 с (между ними режим не переключается, полоса не мигает); доля — от наибольшего лага с начала догона, округляется вниз и, пока идёт догон, не больше 99% (на хвосте, при лаге в секунды, — 99%; конец догона — исчезновение полосы), оценка — по снижению лага за последние 30 с; пока лаг с начала догона не изменился (он обновляется раз в 10 с), оценки нет — только доля; `лаг не снижается` — если лаг растёт, не менялся дольше 30 с или оценка больше 99 дней. При повторе и остановке полосы нет — только лаг. Цвета — базовые 16 цветов терминала, оттенок задаёт его тема; с `NO_COLOR` блоки различимы по заголовкам, рамкам и колонкам. В узком окне графики и полоса пропадают целиком, а хвосты строк усекаются с `…`.

Режим — `--progress` (`PROGRESS`):

- `auto` (по умолчанию) — панель, если stdout — терминал и `TERM` не `dumb`; иначе (`>file`, `| jq`, `nohup`, `TERM=dumb`) — `plain`;
- `tty` — панель, даже если stdout не терминал (управляющие последовательности попадут в вывод, консольный лог — только WARN и выше);
- `plain` — построчный лог, как описано в [«Логи»](#логи).

С панелью над ней печатаются только WARN и ERROR (и только если `--log-level` их пропускает); INFO (`прогресс`, `DDL применён`, `трафик на машине`) в консоль не идёт — его заменяет панель — и пишется только в `--log-file`. Поэтому с панелью запускайте с `--log-file`: без него при старте WARN `полный лог не пишется: добавьте --log-file`. Строки над панелью уходят в историю терминала — смотрите их прокруткой терминала или `tmux`; полноэкранного режима у панели нет. Строки до старта панели (`лог`, `revision`) и итог при выходе (`остановлен по сигналу`, ERROR с подсказкой, `трафик`) печатаются обычным логом: финальная панель остаётся на экране, итог — под ней.

Перед панелью экран очищается — до первой строки лога, поэтому строки запуска (`revision`, предупреждения, запрос пароля, `файл состояния`) печатаются уже на чистом экране над панелью; стираются только прежние команды терминала. Попадут ли стёртые строки в историю прокрутки, зависит от терминала (`tmux`, VTE — да; xterm, urxvt — нет); полный лог — в `--log-file`. Не очищать — `--no-clear` (`NO_CLEAR=true`).

Панель читает клавиатуру: терминал на время панели переводится в raw-режим, набранное и Enter не отображаются и не сбивают кадр. Ввод — stdin, если он терминал, иначе `/dev/tty` (запуск с `< /dev/null`); при запуске в фоне (`&`) панель клавиатуру не читает. Клавиши:

- **Ctrl+C** — остановка, как по SIGINT без панели: пачка дописывается, аренда снимается, код выхода `0` (см. [«Гарантии»](#гарантии)); на русской раскладке в kitty-совместимых терминалах (kitty, ghostty, wezterm, foot) тоже;
- **Ctrl+Z** — приостановка; продолжать только `fg`: `bg` не работает — возврат raw-режима из фоновой группы останавливает процесс на SIGTTOU. Без управления заданиями (контейнер `make run`, `ssh -t host cmd`, `script`), при унаследованном игнорировании SIGTSTP (`trap '' TSTP` в скрипте) и вне Linux Ctrl+Z игнорируется. Приостановка останавливает и репликацию: если пауза дольше аренды (60 с), базу может забрать другой процесс, и после `fg` процесс выйдет с `аренда базы цели потеряна` (см. [«Несколько процессов»](#несколько-процессов)). Для работы в фоне — `tmux` или `--progress plain`;
- **Ctrl+\\** — дамп горутин (`SIGQUIT`): панель сначала завершается и восстанавливает терминал, дамп печатается в обычный терминал; процесс выходит сразу с кодом `2`, хвост не дописывается и аренда не снимается — новый процесс на эту базу стартует после её истечения (до 60 с);
- прочий ввод игнорируется.

Если панель зависла — `kill -INT <pid>` (остановка) или `kill -QUIT <pid>` (дамп) из другого терминала. Если процесс убит `SIGKILL`, упал паникой не в основной горутине или фатальной ошибкой рантайма Go, терминал остаётся в raw-режиме со скрытым курсором и расширенной клавиатурой: наберите вслепую `reset` и Enter (если Enter не срабатывает — Ctrl+J).

Посмотреть панель без кластеров — демо на мок-данных:

```sh
make panel-demo && ./bin/mongo-replicator-panel
```

Сценарий: запуск (2 с), догон с лагом больше суток, с 30-й секунды — медленный хвост догона (лаг от 2 мин к 0 за 60 с: видны полоса, оценка и выход из догона; первые 30 с хвоста в окне оценки ещё быстрый догон, и оценка близка к нулю), ровный поток с 90-й секунды, повтор с ошибкой на 100–110-й секунде (к этому времени высокие точки догона ушли из графиков, и провал на них виден), DDL после 20-й секунды, WARN над панелью. Экран перед панелью демо очищает всегда. Панель, выбор ввода и клавиши — те же, что у `mongo-replicator`; Ctrl+C печатает итоговый кадр и строку `остановлен по сигналу; применено N (демо)`. Если stdout не терминал, демо выходит с кодом `2`.

## Мониторинг лага

Лог `прогресс` раз в 10 с:

| Поле | Значение |
|---|---|
| `applied` | всего применено операций с запуска |
| `rate` | операций/с за последний интервал |
| `applied_at` | время применённой позиции (RFC3339, UTC) |
| `lag` | лаг строкой (`1m5s`) |
| `lag_sec` | лаг в секундах, число — для алертов по JSON-логу в файле (`--log-file`) |
| `src_in` … `dst_out_bps` | трафик процесса, см. [«Трафик»](#трафик) |

Лаг = текущее время кластера источника (`operationTime` ответа `ping`) минус время **применённой** позиции — токена последнего сохранённого чекпойнта. Чекпойнт двигается только после записи данных на цель с `w:majority`, значит всё до этой позиции уже на цели; прочитанные, но ещё не записанные события в лаг входят. Обе величины — время кластера источника, часы машины репликатора не участвуют.

На простаивающем источнике лаг не растёт: поток отдаёт post-batch resume token, который двигается вместе с oplog источника (периодические no-op, записи в другие базы), и чекпойнт сохраняется с ним.

Лог пишется и пока репликация застряла в повторах (WARN `ошибка репликации, повтор`): позиция стоит, `lag_sec` растёт — алерт по нему срабатывает. Поля `applied_at`, `lag`, `lag_sec` отсутствуют, пока на цели нет чекпойнта; `lag` и `lag_sec` — также если `ping` источника не удался (DEBUG с ошибкой — виден только при `--log-level debug` или `--log-file-level debug`; репликация не прерывается).

`clusterTime` в чекпойнте на цели — то же время применённой позиции, поэтому лаг можно посчитать и без логов. В mongosh, подключённом к источнику:

```js
const dst = new Mongo("mongodb://user:pass@dst1:27017/?replicaSet=rsdst");
const applied = dst.getDB("urlshrinker_v2")._replicator_checkpoint.findOne().clusterTime;   // --dst-db
const now = db.adminCommand({ping: 1}).operationTime;
now.t - applied.t;   // лаг, сек
```

## Трафик

Каждый процесс считает байты, прошедшие через сокеты драйвера к источнику и к цели, — реальный сетевой трафик (уже после TLS и сжатия) для оценки стоимости и нагрузки на сеть.

| | Что |
|---|---|
| считается | поток (`aggregate`, `getMore`) и `updateLookup`; запись на цель; чекпойнт и аренда; `ping`; heartbeat и RTT-мониторинг драйвера; аутентификация и TLS-рукопожатие |
| не считается | заголовки TCP/IP и ретрансмиты; DNS (в т.ч. SRV для `mongodb+srv`); другие программы на машине; внутренняя репликация кластеров; в файле состояния — последние ≤10 с перед `kill -9` |

Направления:

| Поле | |
|---|---|
| `src_in` | получено от источника — основной объём: события потока с полными документами; для кластера источника это исходящий (egress) трафик |
| `src_out` | отправлено источнику: запросы |
| `dst_in` | получено от цели: ответы |
| `dst_out` | отправлено на цель — основной объём записи: документы пачек |

Где видно:

- **лог процесса** — с начала процесса, после рестарта счётчики с нуля: в `прогресс` раз в 10 с — `src_in`, `src_out`, `dst_in`, `dst_out` (байты) и `src_in_bps` … `dst_out_bps` (средняя скорость за интервал, байт/с); при выходе — INFO `трафик` с четырьмя суммами и `uptime`;
- **файл состояния** — по базе цели за все запуски на этой машине: `traffic.src_in` … `traffic.dst_out` (байты); обновляется раз в 10 с и при выходе (см. [«Состояние на машине»](#состояние-на-машине));
- **сводка** — раз в минуту (первая — вскоре после старта) процесс суммирует все файлы каталога состояния: INFO `трафик на машине` (`processes` — файлов, `active` — из них обновлённых за последние 30 с, `src_in` … `dst_out` — суммы в байтах), в панели — строка `машина`. Трафик остановленных процессов входит в сводку, пока лежит их файл. Не удалась — WARN `сводка трафика на машине не получена`.

Неточность накопления: после `kill -9` или падения машины теряется прирост с последней записи файла (≤10 с); то же — при выходе, когда цель недоступна: подтвердить аренду не удалось, владелец базы неизвестен, и последняя запись файла пропускается. Последняя запись — до снятия аренды: следующий процесс на эту базу читает файл уже с ней.

Облако насчитает на несколько процентов больше: заголовки TCP/IP, ретрансмиты, DNS и трафик других программ сюда не входят.

## Состояние на машине

Накопленный трафик хранится не на цели, а в файлах на машине, где работает репликатор: учёт трафика нужен по машине, а потеря файла репликацию не ломает. Файл — по одному на процесс (базу цели и кластер цели).

Каталог — `--state-dir` (`STATE_DIR`); по умолчанию `$XDG_STATE_HOME/mongo-replicator` (только если `XDG_STATE_HOME` — абсолютный путь), иначе `~/.local/state/mongo-replicator`. Каталог создаётся при старте (права `0750`); не удалось — выход с кодом `2` до подключения. Путь файла процесса — в INFO `файл состояния` (`file`) при старте.

Сводка — сумма всех файлов каталога, поэтому с каталогом по умолчанию она фактически по пользователю: процессы другого пользователя той же машины пишут в свой `~/.local/state`. Чтобы сводка была по всем пользователям машины, дайте им общий `--state-dir` с общей группой — файлы создаются с правами `0640`:

```sh
sudo install -d -m 2770 -g repl /var/lib/mongo-replicator   # группа repl — все, кто запускает репликатор
./bin/mongo-replicator --state-dir /var/lib/mongo-replicator --db urlshrinker
```

Имя файла — `<dst-db>.<8 hex>.json`, где `8 hex` — начало SHA-256 ключа кластера цели. Ключ считается по URI `--dst` как написан, без пользователя, пароля и параметров:

- `mongodb+srv://Cluster0.example.net/...` — `srv:cluster0.example.net` (не разрешённые из SRV хосты: при `srvMaxHosts` это случайное подмножество);
- `mongodb://dst2,dst1:27017/...` — хосты в нижнем регистре, порт `27017` по умолчанию, отсортированные: `dst1:27017,dst2:27017`.

Тот же кластер с другим набором хостов в URI — другой файл. Формат:

```json
{"db": "urlshrinker", "dst_db": "urlshrinker_v2", "cluster": "dst1:27017,dst2:27017",
 "owner": "host:12345:1a2b3c4d", "started_at": "2026-10-15T09:00:00Z", "updated_at": "2026-10-15T12:01:30Z",
 "traffic": {"src_in": 3328599654, "src_out": 12582912, "dst_in": 41943040, "dst_out": 3113851289}}
```

`traffic` — накоплено за все запуски на этой машине; `owner` и `started_at` — последний запущенный процесс, перезаписываются при каждом старте; `updated_at` — последняя запись (по нему считается `active` в сводке); `cluster` — ключ кластера цели.

- Файл читается один раз за процесс — после проверки пары баз чекпойнта: с неверным `--db` (`ErrDBMismatch`) он не трогается. Счёт продолжается от записанного в файле.
- Затем файл записывается сразу, раз в 10 с и при выходе. Запись атомарная (временный файл и `rename`): после сбоя остаётся старое или новое содержимое. Ошибка записи — WARN `файл состояния не записан`, репликация продолжается.
- Файл обновляется и в паузах цикла повторов (WARN `ошибка репликации, повтор`), пока аренда свежая (последнее продление или захват не старше 40 с): процесс остаётся единственным владельцем базы цели и в сводке остаётся активным. Без связи с целью дольше 40 с запись приостанавливается — аренду может забрать другой процесс с этой же машины и писать в тот же файл; после нового захвата следующая запись содержит всё накопленное.
- При выходе файл записывается, только если аренда была за этим процессом: второй процесс на ту же базу, не получивший аренду (`ErrLeaseHeld`), файл не трогает.
- Битый файл переносится в `<имя>.corrupt-<время UTC>`, файл другой пары баз или другого кластера — в `<имя>.mismatch-<время UTC>`, счёт начинается с нуля (WARN `... перенесён в сторону, счёт трафика — с нуля`). История не стирается, но в сводку такие файлы не входят. Не удалось перенести (в том числе имя переноса уже занято — второй перенос за ту же секунду) — WARN, трафик в файл не пишется до следующего запуска.
- Сводка — все `*.json` каталога: `processes` — число файлов, в том числе остановленных процессов; `active` — обновлённые за последние 30 с. Нечитаемый файл пропускается с WARN `файл состояния пропущен в сводке`.
- Сбросить счёт — остановить процесс и удалить его файл. Удаление чекпойнта или базы цели файл не трогает.

Общий итог по нескольким машинам — вручную: соберите файлы с машин в один каталог и сложите, например в GiB:

```sh
mkdir -p all/host1 all/host2
scp 'host1:.local/state/mongo-replicator/*.json' all/host1/
scp 'host2:.local/state/mongo-replicator/*.json' all/host2/
jq -s 'map(.traffic) | {src_in: (map(.src_in) | add), src_out: (map(.src_out) | add),
    dst_in: (map(.dst_in) | add), dst_out: (map(.dst_out) | add)}
    | map_values(. / 1073741824 * 100 | round / 100)' all/*/*.json
```

По базам — `jq -s 'group_by(.dst_db) | ...'`.

## Ограничения

Событие change stream не может быть больше 16 МБ. Репликатор убирает из событий `updateDescription` (ему нужен только `fullDocument`), поэтому обновления документов до ~16 МБ проходят. Если документ так близок к 16 МБ, что не помещается в событие даже без `updateDescription`, сервер отвечает ошибкой 10334, и репликатор выходит с кодом `1`: продолжить можно только новой полной заливкой с `--start-ts` после этого изменения.

Поток читается с `fullDocument: updateLookup`: для `update` на цель пишется текущая версия документа, найденная на источнике в момент чтения события. Отсюда два случая потери данных:

- **(a) updateLookup после rename или drop + recreate.** Если к моменту чтения `update` коллекцию уже переименовали или пересоздали, документ не находится, `fullDocument` пустой и событие пропускается — без записи в лог: так же пропускается и безвредный `update`, за которым следует `delete`, и отличить их по событию нельзя. На цели в новой коллекции остаётся старая версия документа. Воспроизводит `TestLimitationUpdateLookupAfterRename`.
- **(b) rename или drop + recreate в окне `--start-ts` → конец дампа.** Дамп уже содержит итоговую коллекцию `b` целиком, а повтор потока создаёт на цели `a` только из событий окна и переименовывает её в `b` с `dropTarget` — документы `b`, не тронутые в окне, уничтожаются. Воспроизводит `TestLimitationRenameInCatchUpWindow`. Для drop + recreate репликатор останавливается на `drop` (коллекция есть на цели из дампа); потеря происходит, если применить его через `--apply-drop`.

Оба теста помечены `t.Skip`; без него они падают, пока ограничение не устранено. Будущий фикс для (a) — включить на источнике `changeStreamPreAndPostImages` и читать поток с `fullDocument: required`: post-image сохраняется в момент изменения и не зависит от последующих rename/drop. (b) так не устраняется: документов `b`, не тронутых в окне, в потоке нет вовсе, и способ чтения документа их не вернёт — для (b) нужно отдельное решение. До тех пор не выполняйте rename и drop + recreate коллекций в окне дампа и пока репликатор отстаёт.

Rename коллекций внутри реплицируемой базы поддерживается. Перенос коллекций между базами (`renameCollection` из одной базы в другую) не предусмотрен; на 8.0 поток уровня базы видит его так (закреплено `TestIntegrationCrossDBRenameIn` / `TestIntegrationCrossDBRenameOut`):

- перенос **наружу** (`X.a → Y.b`) — приходит только `drop X.a`: репликатор останавливается, как на любом `drop` (см. [«Удаления»](#удаления));
- перенос **внутрь** (`Y.b → X.a`) — приходит как создание временной коллекции, её индексы, вставка всех документов и rename в `X.a` (поверх существующей `X.a` — с `dropTarget`): на цели появляется копия коллекции, репликация продолжается.

### Удаления

Удаления на источнике не предусмотрены: `drop` коллекции, которая есть на цели, перенос коллекции в другую базу (приходит как `drop`) и `dropDatabase` на цели **не применяются** — репликатор выходит с кодом `1` и ERROR с подсказкой. Всё до удаления уже на цели, чекпойнт стоит перед удалением, рестарт с теми же опциями снова останавливается на нём же.

`dropDatabase` ловится уже на первом `drop`: сервер сначала присылает `drop` по каждой коллекции базы (в произвольном порядке), затем `dropDatabase`, затем `invalidate`. Поэтому подсказка в логе будет про коллекцию; если разрешить `drop` всех коллекций, репликатор дойдёт до `dropDatabase` и остановится на нём — `dropDatabase` не разрешается никогда.

Исключения — `drop` применяется или пропускается без остановки:

- временные коллекции самой MongoDB (`tmp.agg_out.<UUID>` от `$out`/`mapReduce`, `tmpXXXXX.renameCollection`, `tmpXXXXX.convertToCapped.*`) — `drop` применяется без остановки (INFO `DDL применён`, без WARN); такой `drop` даёт, например, неудачный `$out`. Имя сверяется с точным форматом, который генерирует MongoDB: пользовательские коллекции с похожими именами (`tmp.backup`, `tmp.agg_out.archive`) под исключение не попадают;
- коллекции, которой нет на цели (view, time-series — их репликатор не переносит, или уже удалённая), — `drop` пропускается с WARN `drop <ns>: на цели такой коллекции нет (view/time-series или уже удалена)`: терять нечего;
- view, который на цели есть (например, восстановлен из заливки), — `drop` применяется без остановки: данных во view нет.

Каждый `$out` (и `mapReduce`) создаёт на цели `tmp.agg_out.*` и пишет WARN `коллекция создана без опций источника, проверьте вручную` — это шум, не ошибка: временная коллекция сразу переименовывается в целевую.

### После остановки на drop

В логе — ERROR с подсказкой `... перезапустите с --apply-drop <ns>`, в поле ошибки — `на источнике удалена коллекция <ns>, на цели не применено`. Если удаление ожидаемое, перезапустите с разрешением:

```sh
./bin/mongo-replicator --apply-drop urlshrinker.links   # или APPLY_DROP=urlshrinker.links
```

- `<ns>` — namespace **источника** (`--db`), даже если `--dst-db` другая: удалена будет `<dst-db>.links`;
- разрешение одноразовое в пределах запуска: коллекция вычёркивается сразу после применения `drop`, ещё до сохранения чекпойнта; повторный `drop` той же коллекции (например, после пересоздания) снова останавливает репликатор. При рестарте с тем же `--apply-drop` разрешение действует заново — уберите коллекцию из `APPLY_DROP`/команды запуска после применения (об этом напоминает WARN `разрешены drop: ...` при старте);
- сбой между `drop` на цели и сохранением чекпойнта безопасен. Повтор в том же процессе снова получит этот `drop`, но разрешения уже нет, а коллекции на цели тоже нет — `drop` пропускается с WARN `drop <ns>: на цели такой коллекции нет (view/time-series или уже удалена)`: это ожидаемо, коллекция удалена этим же `drop`. После рестарта с тем же `--apply-drop` `drop` применится снова, `drop` несуществующей коллекции игнорируется;
- если `drop` (и пересоздание) пришлись на окно `--start-ts` → конец дампа, `--apply-drop` не применяйте: дамп уже содержит пересозданную коллекцию, а `drop` уничтожит её документы, не тронутые в окне (см. [«Ограничения»](#ограничения), (b)). Нужна новая заливка с более поздним `--start-ts`;
- `dropDatabase` так не продолжить — только новая полная заливка (см. [«Восстановление»](#восстановление)).

Уникальные индексы. Идемпотентность replace-upsert по `_id` держится, пока на цели нет уникальных вторичных индексов: при повторе старая версия документа может конфликтовать с более новым состоянием другого документа (E11000), и репликация встаёт в бесконечный повтор (см. «Гарантии»). Устраняется вручную на цели: удалите мешающий документ — последующие события потока его восстановят.

Не поддерживаются (событие пропускается с WARN в логе, переносите вручную):

- `collMod` и прочие изменения опций существующей коллекции;
- views — не создаются;
- опции `create` (capped, validator, collation, timeseries и т.п.) — коллекция создаётся обычной;
- шардирование (`shardCollection`, `refineCollectionShardKey` и т.п.).
