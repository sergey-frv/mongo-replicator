# mongo-replicator

Односторонняя репликация MongoDB через change streams.

Назначение: догонять целевой кластер более старой версии (например, 5.0) до источника более новой (например, 8.0), когда oplog replay, `mongorestore` и `mongosync` неприменимы из-за разницы версий.

Переносятся DML (`insert`, `update`, `replace`, `delete`) и DDL `create`, `drop`, `dropDatabase`, `rename`, `createIndexes`, `dropIndexes`. Базы `admin`, `config`, `local` и `_replicator` не реплицируются.

Два режима, выбор обязателен:

- `--db X` — только база `X`: поток уровня базы, на источнике достаточно прав на чтение `X`;
- `--all-dbs` — все базы, кроме служебных: поток уровня кластера, на источнике нужна `readAnyDatabase`.

## Требования

- источник: replica set, MongoDB 6.0+ (нужен `showExpandedEvents` для DDL);
- цель: на неё пишет только репликатор;
- на цели уже восстановлен полный дамп источника, а `--start-ts` указывает на момент **до** начала этого дампа и ещё попадает в окно oplog источника;
- права на источнике и цели — см. [«Права»](#права);
- сборка: Go 1.26 (`make build` также выполняет `go mod tidy` и `go mod vendor`); тесты, линтер и `make run` — Docker с compose.

## Запуск

```sh
make build    # bin/mongo-replicator, ревизия из git describe
```

| Опция | Env | По умолчанию | |
|---|---|---|---|
| `--src` | `SRC_URI` | обязательна | URI источника |
| `--dst` | `DST_URI` | обязательна | URI цели |
| `--start-ts` | `START_TS` | `0` | unix-сек, с которых читать поток при отсутствии чекпойнта |
| `--batch` | `BATCH_SIZE` | `1000` | максимум операций в одной пачке записи, `>= 1` |
| `--dbg` | `DEBUG` | `false` | debug-уровень и человекочитаемый вывод вместо JSON |
| `--db` | `DB` | — | реплицировать только эту базу (поток уровня базы) |
| `--all-dbs` | `ALL_DBS` | `false` | реплицировать все базы, кроме служебных (поток уровня кластера) |

Нужно указать ровно одно из `--db` / `--all-dbs`, иначе выход с кодом `2`: режим всех баз включается только явно. Пустой `DB=` — то же, что `--db` не задан. Имя базы проверяется по правилам MongoDB (без `/\. "$` и NUL, не длиннее 63 байт); служебные базы (`admin`, `config`, `local`, `_replicator`) указать нельзя.

Опции принимаются только с двумя дефисами: `--src`, а не `-src`, как было в первой версии (`-src` разбирается как набор коротких флагов `-s -r -c`).

```sh
./bin/mongo-replicator \
    --src "mongodb://user:pass@src1:27017,src2:27017/?replicaSet=rs8" \
    --dst "mongodb://user:pass@dst1:27017,dst2:27017/?replicaSet=rs5" \
    --db urlshrinker \
    --start-ts 1791900000
```

Все базы — то же с `--all-dbs` вместо `--db urlshrinker`.

URI удобно держать в `cmd/mongo-replicator/.env` (он в `.gitignore`):

```sh
# cmd/mongo-replicator/.env
SRC_URI=mongodb://user:pass@src1:27017/?replicaSet=rs8
DST_URI=mongodb://user:pass@dst1:27017/?replicaSet=rs5
DB=urlshrinker
```

```sh
set -a; . cmd/mongo-replicator/.env; set +a
./bin/mongo-replicator --start-ts 1791900000
```

`--start-ts` нужен только на первом запуске: дальше поток продолжается с чекпойнта на цели, а опция игнорируется.

Чекпойнт помнит, для какой базы он записан (поле `db`, `""` — все базы). Сменить базу или режим поверх существующего чекпойнта нельзя — выход с кодом `1` (см. [«Восстановление»](#восстановление)).

Новая полная заливка (например, после выхода с кодом `1` из-за выпадения из oplog): чекпойнт хранится на цели в `_replicator`, в дамп источника он не входит, поэтому перед запуском с новым `--start-ts` его нужно удалить вручную — `db.getSiblingDB('_replicator').checkpoint.drop()`.

### Права

| Режим | Источник | Цель |
|---|---|---|
| `--all-dbs` | `readAnyDatabase` (`find` + `changeStream` на всех базах) | `readWrite` на реплицируемые базы и `_replicator` + `dropDatabase` на них (например, `readWriteAnyDatabase` + `dbAdminAnyDatabase`) |
| `--db X` | `read` на `X` | `readWrite` на `X` и `_replicator` + `dropDatabase` на `X` (`dbAdmin@X` или своя роль) |

Поток уровня кластера с правами только на одну базу падает с кодом 13 (`Unauthorized`) — для такого пользователя нужен `--db`.

`_replicator` на цели заранее создавать не нужно: база и коллекция `checkpoint` создаются автоматически при первом сохранении чекпойнта, достаточно `readWrite` на `_replicator`.

Без `dropDatabase` на цели событие `dropDatabase` источника падает с кодом 13; эта ошибка не перманентная, поэтому репликатор бесконечно повторяет её (WARN `ошибка репликации, повтор`) и до остановки по `dropDatabase` (см. [«Ограничения»](#ограничения)) дело не доходит.

### Проверка перед запуском

В mongosh под пользователем репликатора.

Источник — поток по базе открывается (`null` без ошибки — права есть, код 13 — нет):

```js
const cs = db.getSiblingDB("urlshrinker").watch([], {showExpandedEvents: true});
cs.tryNext();
cs.close();
```

Источник — `--start-ts` ещё в окне oplog (`null` без ошибки — в окне, код 286 `ChangeStreamHistoryLost` — выпал, нужна более свежая заливка):

```js
const cs = db.getSiblingDB("urlshrinker").watch([], {startAtOperationTime: Timestamp({t: 1791900000, i: 0})});
cs.tryNext();
cs.close();
```

Для `--all-dbs` — то же через `db.getMongo().watch(...)` вместо `db.getSiblingDB(...).watch(...)`.

Цель — запись в `_replicator` с `w: "majority"`:

```js
const r = db.getSiblingDB("_replicator");
r.probe.insertOne({_id: 1}, {writeConcern: {w: "majority"}});
r.probe.drop();
```

Цель — право `dropDatabase` на базу (непустой результат — есть):

```js
db.getSiblingDB("urlshrinker").runCommand({connectionStatus: 1, showPrivileges: true})
    .authInfo.authenticatedUserPrivileges
    .filter(p => p.resource.db === "urlshrinker" && p.actions.includes("dropDatabase"));
```

### Локальная проверка

```sh
make docker-volumes   # один раз: тома go-build-cache и go-lint-cache
make run              # mongo-src (8.0, rs8) + mongo-dst (5.0, rs5) и репликатор с --all-dbs и --start-ts = сейчас
```

Запуск против локальных mongo — только через `make run`: в rs-конфиге члены записаны как `mongo-src`/`mongo-dst`, с хоста эти имена не резолвятся.

После `make test-integration` на `mongo-dst` остаётся чекпойнт последнего теста, и `make run` продолжит с него, игнорируя `--start-ts`. Чтобы начать с чистого листа — `make down`.

### Разработка

```sh
make test               # юнит-тесты, mongo не нужна
make test-integration   # интеграционные тесты против mongo-src и mongo-dst, строго последовательно (-p 1): общий чекпойнт и поток
make lint               # golangci-lint
make down               # остановить контейнеры и удалить их тома
```

Интеграционные тесты берут кластеры из `IT_SRC_URI`/`IT_DST_URI` (заданы только в сервисе `app` в `docker-compose.yml`), удаляют `_replicator.checkpoint` на цели и базы `it_*` на обоих кластерах. Отдельные переменные нужны, чтобы тесты не ушли на рабочие кластеры из `SRC_URI`/`DST_URI` загруженного `.env`. Запускайте их через `make test-integration`.

## Гарантии

- at-least-once: после сбоя поток продолжается с последнего сохранённого resume token, события после него читаются повторно;
- операции идемпотентны: insert/update/replace применяются как replace-upsert полного документа по `_id`, delete — по `_id`; повторное применение даёт то же итоговое состояние. DDL «уже есть» / «уже нет» при повторе игнорируется;
- чекпойнт хранится на цели (`_replicator.checkpoint`) и двигается только после успешной записи данных; клиент цели работает с `w:majority`, чтобы чекпойнт не обогнал данные при failover, а сам чекпойнт читается только с primary, даже если в `--dst` задан `readPreference` (устаревший токен с отстающей secondary повторил бы rename поверх применённого состояния);
- после DDL чекпойнт сохраняется сразу, чтобы rename/drop не повторялись после рестарта;
- любая ошибка, кроме перманентных (см. коды выхода), — повтор через 5 с без выхода. Так переживаются сеть и failover, но так же бесконечно повторяются и постоянные ошибки (цель не приняла документ или DDL): чекпойнт стоит перед проблемным событием, в логе каждые 5 с WARN `ошибка репликации, повтор`. После исправления цели репликация продолжается сама.

Логи — JSON в stdout (поля `m`, `e`, `l`, `t`). Раз в 10 с — INFO `прогресс` (см. [«Мониторинг лага»](#мониторинг-лага)); применённый DDL — INFO `DDL применён` (`op`, `ns`, `to`); пропущенные события — WARN.

Коды выхода:

| Код | Причина |
|---|---|
| `0` | остановка по SIGINT/SIGTERM (незаписанный хвост будет перечитан при следующем запуске); `--help` |
| `1` | точка возобновления выпала из oplog источника (нужна новая полная заливка цели); нет ни чекпойнта, ни `--start-ts`; чекпойнт записан для другой базы или режима (`ErrDBMismatch`); отслеживаемая база удалена на источнике (`dropDatabase`, `ErrStreamInvalidated`); некорректный URI или кластер недоступен (`Ping` за 10 с) |
| `2` | ошибка опций, в т.ч. не указано или указаны оба из `--db` / `--all-dbs`, некорректное имя базы |

Перманентные ошибки не повторяются: в лог пишется ERROR с подсказкой оператору, затем выход с кодом `1`.

### Восстановление

- **Выпадение из oplog** — новая полная заливка цели, удаление чекпойнта, запуск с новым `--start-ts` (см. «Запуск»).
- **`ErrDBMismatch`** (`чекпойнт записан для другой базы`): если опции перепутаны — запустите с прежними `--db` / `--all-dbs`, чекпойнт подхватится. Если базу или режим нужно сменить: остановите репликатор, удалите чекпойнт (`db.getSiblingDB('_replicator').checkpoint.drop()` на цели), залейте нужную базу на цель заново и запустите с новыми опциями и новым `--start-ts` до начала дампа.
- **`ErrStreamInvalidated`** (`поток инвалидирован (dropDatabase базы)`): всё до `dropDatabase` включительно уже применено, база на цели удалена. Продолжить старый поток нельзя — рестарт без удаления чекпойнта снова получает `invalidate` и выходит с `1`. Когда база на источнике создана заново: удалите чекпойнт, залейте базу на цель и запустите с новым `--start-ts`.

## Мониторинг лага

Лог `прогресс` раз в 10 с:

| Поле | Значение |
|---|---|
| `applied` | всего применено операций с запуска |
| `rate` | операций/с за последний интервал |
| `applied_at` | время применённой позиции (RFC3339, UTC) |
| `lag` | лаг строкой (`1m5s`) |
| `lag_sec` | лаг в секундах, число — для алертов по логам |

Лаг = текущее время кластера источника (`operationTime` ответа `ping`) минус время **применённой** позиции — токена последнего сохранённого чекпойнта. Чекпойнт двигается только после записи данных на цель с `w:majority`, значит всё до этой позиции уже на цели; прочитанные, но ещё не записанные события в лаг входят. Обе величины — время кластера источника, часы машины репликатора не участвуют.

На простаивающем источнике лаг не растёт: поток отдаёт post-batch resume token, который двигается вместе с oplog источника (периодические no-op, записи в другие базы), и чекпойнт сохраняется с ним.

Поля `applied_at`, `lag`, `lag_sec` отсутствуют, пока не сохранён первый чекпойнт; `lag` и `lag_sec` — также если `ping` источника не удался (DEBUG с ошибкой, репликация не прерывается).

`clusterTime` в чекпойнте на цели — то же время применённой позиции, поэтому лаг можно посчитать и без логов. В mongosh, подключённом к источнику:

```js
const dst = new Mongo("mongodb://user:pass@dst1:27017/?replicaSet=rs5");
const applied = dst.getDB("_replicator").checkpoint.findOne({_id: "main"}).clusterTime;
const now = db.adminCommand({ping: 1}).operationTime;
now.t - applied.t;   // лаг, сек
```

## Ограничения

Поток читается с `fullDocument: updateLookup`: для `update` на цель пишется текущая версия документа, найденная на источнике в момент чтения события. Отсюда два случая потери данных:

- **(a) updateLookup после rename или drop + recreate.** Если к моменту чтения `update` коллекцию уже переименовали или пересоздали, документ не находится, `fullDocument` пустой и событие пропускается. На цели в новой коллекции остаётся старая версия документа. Воспроизводит `TestLimitationUpdateLookupAfterRename`.
- **(b) rename или drop + recreate в окне `--start-ts` → конец дампа.** Дамп уже содержит итоговую коллекцию `b` целиком, а повтор потока создаёт на цели `a` только из событий окна и переименовывает её в `b` с `dropTarget` — документы `b`, не тронутые в окне, уничтожаются. Воспроизводит `TestLimitationRenameInCatchUpWindow`.

Оба теста помечены `t.Skip`; без него они падают, пока ограничение не устранено. Будущий фикс — включить на источнике `changeStreamPreAndPostImages` и читать поток с `fullDocument: required`: post-image сохраняется в момент изменения и не зависит от последующих rename/drop. До тех пор не выполняйте rename и drop + recreate коллекций в окне дампа и пока репликатор отстаёт.

Rename коллекций внутри реплицируемой базы поддерживается. Перенос коллекций между базами (`renameCollection` из одной базы в другую) в режиме `--db` не предусмотрен и отдельно не обрабатывается. Если он всё же случится, на 8.0 поток уровня базы видит его так (закреплено `TestIntegrationSingleDBCrossDBRename`):

- перенос **наружу** (`X.a → Y.b`) — приходит только `drop X.a`: коллекция удаляется на цели, в `Y` на цели ничего не появляется;
- перенос **внутрь** (`Y.b → X.a`) — приходит как создание временной коллекции, её индексы, вставка всех документов и rename в `X.a`: на цели появляется копия коллекции.

`dropDatabase` реплицируемой базы в режиме `--db` применяется на цели (база удаляется), после чего сервер закрывает поток событием `invalidate` и репликатор выходит с кодом `1` (`ErrStreamInvalidated`, см. [«Восстановление»](#восстановление)).

Уникальные индексы. Идемпотентность replace-upsert по `_id` держится, пока на цели нет уникальных вторичных индексов: при повторе старая версия документа может конфликтовать с более новым состоянием другого документа (E11000), и репликация встаёт в бесконечный повтор (см. «Гарантии»). Устраняется вручную на цели: удалите мешающий документ — последующие события потока его восстановят.

Не поддерживаются (событие пропускается с WARN в логе, переносите вручную):

- `collMod` и прочие изменения опций существующей коллекции;
- views — не создаются;
- опции `create` (capped, validator, collation, timeseries и т.п.) — коллекция создаётся обычной;
- шардирование (`shardCollection`, `refineCollectionShardKey` и т.п.).
