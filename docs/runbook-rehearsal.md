# Runbook: репетиция перелива

Репликатор на машине будущей переливки читает **боевой** источник с живыми записями и пишет в **пустую** mongo 4.4 в Docker — стенд `deploy/rehearsal/` со схемой источника. Дампа нет: репетиция проверяет сам репликатор. Готовность — два критерия: **данные совпадают** (`mongo-replicator verify`) и **процесс устойчив** (сценарии F1–F7).

Ниже `$DB` — база источника, `$DST_DB` — база цели (может совпадать с `$DB`), команды — из корня репозитория.

## 1. Предпроверка

- Пройти README «Проверка перед запуском» под пользователем репликатора на источнике: поток по базе открывается (`showExpandedEvents`). Пробу `START_TS` делают в разделе 3, пробу цели — в разделе 2, под `repl`.
- На машине:
  - Docker с compose;
  - `mongosh` с хоста — пакет `mongodb-mongosh` (Node.js, AVX не нужен, серверы 4.2+): скрипты стенда идут через него, в образе `mongo:4.4` `mongosh` нет;
  - бинарник: `make build` (нужен Go 1.26) или собрать на машине разработки `CGO_ENABLED=0 make build` (статический, без зависимости от glibc машины) и скопировать `bin/mongo-replicator`;
  - `tmux`, `jq` — для журнала.
- Цель репетиции — `mongo:4.4`: на машине переливки mongo 5.0+ не запускается. Исходим из того, что возможности 8.0, которых нет в 4.4 (clustered, time-series, `changeStreamPreAndPostImages` и т. п.), не используются ни источником, ни репликатором, ни `verify`. Если `copy-schema.js` или `verify --schema-only` упрутся в такую возможность — это вывод репетиции, в журнал.
- Свободное место на томе Docker: цель получает только документы, изменённые за репетицию. Оценка — после первых минут догона (раздел 3): `rate` из лога `прогресс` (операций/с) × средний размер документа (`db.getSiblingDB("<база источника>").stats().avgObjSize` на источнике) × длительность репетиции в секундах, с запасом в 2 раза. Не хватает — остановить репликатор (Ctrl+C) до заполнения диска.

## 2. Стенд

Каталог репетиции и общие переменные — один файл на все окна:

```sh
mkdir -p ~/rehearsal
cat > ~/rehearsal/env <<'EOF'
R=$HOME/rehearsal
SRC_URI='mongodb://<пользователь>@<хост1>:27017,<хост2>:27017/?replicaSet=<rs>&authSource=admin'
DST_URI='mongodb://repl@127.0.0.1:27117/?directConnection=true'
DB=<база источника>
DST_DB=<база цели>
STATE_DIR=$HOME/rehearsal/state
EOF
set -a; . ~/rehearsal/env; set +a     # в каждом новом окне tmux
```

URI — в одинарных кавычках, без паролей: пароли спросит терминал (README «Пароли»). У цели **везде** `directConnection=true` — у репликатора, `verify` и `mongosh`: без него драйвер пойдёт на `localhost:27017` из конфигурации replica set стенда, а там может быть другая mongod.

1. Пароль root стенда и запуск:

   ```sh
   cp deploy/rehearsal/.env.example deploy/rehearsal/.env   # задать MONGO_INITDB_ROOT_PASSWORD
   docker compose -f deploy/rehearsal/docker-compose.yml up -d --wait
   ```

   `--wait` возвращается, когда healthcheck видит primary (первый старт — до минуты: keyfile, root, `rs.initiate`).

2. Пользователь `repl` с `readWrite` только на `$DST_DB` — так репетиция подтверждает, что этих прав хватает. `mongosh` спросит пароль root, скрипт — пароль `repl`:

   ```sh
   mongosh "mongodb://root@127.0.0.1:27117/admin?directConnection=true" deploy/rehearsal/create-user.js
   ```

   Повторный запуск — ошибка «пользователь уже есть» с командой пересоздания.

3. Проба записи на цель под `repl` — README «Проверка перед запуском», блок «Цель» (`mongosh "$DST_URI"`).

4. Схема источника — коллекции с опциями, индексы, views; данные не читаются. Цель должна быть пустой, иначе скрипт ничего не делает:

   ```sh
   mongosh --nodb --quiet deploy/rehearsal/copy-schema.js
   ```

   Пароли источника и цели скрипт спросит сам. Ошибка создания (опция, которой 4.4 не знает) — остановка с именем коллекции; созданное до неё остаётся — перед повтором удалить базу цели под root (`db.getSiblingDB("<база цели>").dropDatabase()`).

5. Сверка схемы:

   ```sh
   ./bin/mongo-replicator verify --schema-only
   ```

   Код `0` — схемы совпадают. Код `1` — ERROR `схема: расхождение` (`ns`, `reason`): **любое** расхождение разобрать до старта и записать в журнал. Расхождение, которое сервер 4.4 создаёт иначе, чем источник (поле, которое добавляет сам сервер), — кандидат в список нормализации `internal/verify/schema.go`, а не повод пропустить проверку.

## 3. Запуск

1. `START_TS` — час назад, с пробой окна oplog источника:

   ```sh
   START_TS=$(( $(date +%s) - 3600 )); echo "START_TS=$START_TS" >> "$R/env"
   mongosh "$SRC_URI" --quiet --eval "
     const cs = db.getSiblingDB('$DB').watch([], {startAtOperationTime: Timestamp({t: $START_TS, i: 0})});
     cs.tryNext(); cs.close(); print('в окне oplog')"
   ```

   Код 286 `ChangeStreamHistoryLost` — окно короче часа: взять `START_TS` позже (полчаса назад) и записать в журнал длину окна. `START_TS` попадает в `env`: репликатор читает его сам (`START_TS` — env опции `--start-ts`), при найденном чекпойнте он игнорируется.

2. Окна `tmux` (в каждом — `set -a; . ~/rehearsal/env; set +a`), у каждого процесса свой лог:

   | Окно | Команда |
   |---|---|
   | 1 — репликатор | `./bin/mongo-replicator --log-file "$R/repl.log"` |
   | 2 — сверка | `./bin/mongo-replicator verify --since "$START_TS" --rate 200 --log-file "$R/verify.log"` |
   | 3 — оператор | журнал, `mongosh`, `docker`, `ps` |

   В окне 1 — панель статуса (лаг, скорость, ошибки), в окне 2 — INFO `сверка` раз в 10 с: `checked`, `matched`, `defects`, `unverified`, `queue`, `stream_lag` (поток сверки от времени источника), `ckpt_lag` (чекпойнт от потока сверки) — оба в миллисекундах, с шагом в секунду; `checked` включает повторы горячих ключей, поэтому он может быть больше `matched` и без дефектов. Пока на цели нет чекпойнта, `verify` ждёт его с WARN `чекпойнта на цели ещё нет` раз в минуту — это не ошибка.

   Если коллекции или views источника создавались после `START_TS`, репликатор при старте повторяет их `create` и пишет WARN `коллекция создана без опций источника, проверьте вручную` / `view не создаётся автоматически`: здесь это ожидаемо — коллекции уже созданы `copy-schema.js` с опциями (повторный `create` терпится), а опции проверила `verify --schema-only`.

3. Первые минуты — нагрузка сверки. Ключ проверяется, только когда чекпойнт репликатора прошёл время его события, поэтому пока репликатор догоняет час истории, `queue` растёт — это ожидаемо. После догона (лаг < 10 с) смотреть тренд:
   - `queue` и `stream_lag` стоят или падают — `--rate` хватает;
   - растут несколько минут подряд — сверка не успевает за изменениями источника: каждый ключ — два чтения (S1 и S2), `--rate 200` — до ~100 ключей/с. Остановить `verify` (Ctrl+C: позиция записывается) и запустить снова с бо́льшим `--rate`, если источник выдержит, или с `--sample 0.5` (доля ключей по хэшу `_id`; отброшенные — `sampled_out` в итоге). При продолжении `--since` не нужен: позиция — в `$STATE_DIR/verify/`.

   Подобранные `--rate`/`--sample` — в журнал.

4. Догон: дождаться лага < 10 с и записать время и скорость догона:

   ```sh
   jq -r 'select(.m == "прогресс") | [.t, .lag_sec, .rate, .applied] | @tsv' "$R/repl.log" | less
   ```

   Скорость догона — `applied` за время от старта до первой строки с `lag_sec` < 10, делённое на это время.

## 4. Сценарии сбоев

После **каждого** сценария, прежде чем переходить к следующему: лаг < 10 с (панель окна 1), в окне 2 — `defects` не вырос, ERROR `дефект` нет. Итог — строка в журнале.

| | Действие | Ожидание |
|---|---|---|
| F1 | окно 1: Ctrl+C, затем та же команда | выход с кодом `0`, INFO `остановлен по сигналу…`; новый запуск — `продолжаю с сохранённого resume token`, лаг возвращается < 10 с. Сверка продолжает без вмешательства |
| F2 | окно 3: `pgrep -af mongo-replicator` → `kill -9 <pid репликатора>` (не `verify`); окно 1: `stty sane` (панель не вернула терминал из raw-режима), сразу та же команда; через ≥ 60 с — ещё раз | первый перезапуск — код `1`, ERROR `другой процесс реплицирует эту базу; если он упал — аренда истечёт через ≤60 с` (`e`: `аренда базы цели занята: …`); через ≥ 60 с — работает с чекпойнта. События после чекпойнта применяются повторно (at-least-once) — дефектов это не даёт. Трафик в файле состояния теряет последние ≤ 10 с |
| F3 | `docker restart mongo-rehearsal-mongo-target-1` | репликатор не выходит: WARN `ошибка репликации, повтор` / `продление аренды не удалось, повтор`, после подъёма primary продолжает сам (аренда своя). `verify` не выходит: WARN `чекпойнт не прочитан, повторяю` / `пачка сверки не проверена, повторю` |
| F4 | `docker pause mongo-rehearsal-mongo-target-1`, 90 с, `docker unpause …` | WARN `продление аренды не удалось, повтор` раз в 10 с; через 40 с без продления — WARN `ошибка репликации, повтор` с `аренда не продлевается и скоро истечёт` (запись на цель прекращена до истечения аренды), дальше повторы раз в 5 с. После `unpause` — захват своей истёкшей аренды и продолжение с чекпойнта, без выхода. `verify` — как в F3 |
| F5 | окно 3: второй репликатор с тем же `env` и своим логом (`--log-file "$R/repl2.log" --progress plain`) | второй — код `1`, ERROR `другой процесс реплицирует эту базу…`, файл состояния не тронут; первый работает без WARN |
| F6 | окно 2: Ctrl+C, 5 минут, затем `verify` без `--since` | код `0` (дефектов нет), позиция записана; репликатор этого не замечает. Новый запуск — `продолжаю сверку с файла позиции`, поток сверки догоняет (`stream_lag` падает), очередь разбирается |
| F7 | 1–2 ч ровной работы; раз в 15 мин — `ps -o rss= -p <pid репликатора>` и `ps -o rss= -p <pid verify>` в журнал | лаг всё время < 10 с, RSS без монотонного роста, ERROR в `repl.log` нет (кроме F2/F5), `defects` = 0 |

ERROR в логе за период: `jq -c 'select(.l == "error")' "$R/repl.log" "$R/verify.log"`.

Сверено с кодом и тестами аренды:
- F2: аренда — 60 с от времени сервера цели, `kill -9` её не снимает (README «Несколько процессов»); захват истёкшей чужой аренды — `TestIntegrationLeaseExpired`, отказ при живой — `TestIntegrationLeaseHeld`. Новый процесс — новый владелец (`hostname:pid:hex`), поэтому сразу после `kill -9` — `ErrLeaseHeld` с подсказкой и код `1`, а не повторы.
- F4: прекращение записи через 2/3 срока без продления — `errLeaseExpiring`, временная ошибка (`TestIntegrationLeaseExpiringStopsWrites`, сетевой `TestIntegrationNetDstHangLease`); после `unpause` своя истёкшая аренда захватывается снова (`TestIntegrationAcquireLeaseOurs`, «своя истёкшая, никто не забирал»). Если цель стояла дольше, чем драйвер ждёт ответа, первые повторы после `unpause` могут ещё упасть на старых соединениях — это те же WARN.
- F5: второй процесс файл состояния и аренду первого не трогает — `TestIntegrationLeaseHeld`.

## 5. Известные ситуации

- **E11000 по уникальному индексу**: повторяющийся раз в 5 с WARN `ошибка репликации, повтор` с `E11000 duplicate key` — повтор старой версии документа упёрся в более новое состояние другого документа на цели (README «Уникальные индексы»). Удалить на цели мешающий документ (из текста ошибки — индекс и значение ключа; под `repl` или root), репликатор продолжит сам, последующие события восстановят документ. В журнал; на готовность не влияет, если после этого сверка чистая.
- **DDL между `START_TS` и копией схемы** — окно, аналог окна дампа в настоящей переливке:
  - `create` коллекции, которую `copy-schema.js` уже создал, — терпится (код 48);
  - `drop` коллекции, которая есть на цели, — репликатор останавливается с кодом `1`; решение — README «После остановки на drop». В репетиции дампа нет, но `drop` + пересоздание в окне всё равно ведут к ограничению (b) README «Ограничения»: в журнал;
  - события коллекции, которую удалили до копии схемы, создают её на цели upsert-ом **без опций** (README «Ограничения», «Не поддерживаются»): `verify` покажет её в сверке схемы — как известное ограничение (WARN `схема: известное ограничение`), если `create` был в потоке сверки, иначе расхождением.
- **rename/drop во время репетиции** — в журнал: rename при отставании репликатора может потерять обновления (README «Ограничения», (a)) — это честный дефект сверки; `drop` уводит ключи коллекции в «не проверено» с причиной `drop`.

## 6. Стоп-кран нагрузки

Если источник жалуется на нагрузку:

1. Сначала остановить `verify` (окно 2, Ctrl+C) — на репликатор это не влияет. Её основная цена — второй change stream, который повторяет просмотр oplog (без `updateLookup`), и чтения документов (`--rate`). Продолжить — той же командой без `--since`, пока позиция сверки в окне oplog; иначе — ERROR с подсказкой удалить файл позиции и начать с более позднего `--since`.
2. Если мало — остановить репликатор (окно 1, Ctrl+C). Он продолжит с чекпойнта, пока позиция в окне oplog; выпал — нужна новая репетиция с нуля (раздел 8, уборка).

Обе остановки — в журнал с временем.

## 7. Финал

1. Окно 2: Ctrl+C (позиция записана). Репликатор **продолжает работать** — финальная сверка ждёт его чекпойнт.
2. Убедиться, что позиция репликатора ушла за последние интересующие записи (лаг < 10 с при живых записях источника), и запустить:

   ```sh
   ./bin/mongo-replicator verify --until-caught-up --log-file "$R/verify.log"
   ```

   Сверка продолжает с позиции, догоняет чекпойнт, проверяет все ключи с временем события строго до него и выходит. Если источник затих, последнее событие может совпадать с позицией чекпойнта и в цель не входит (позиция сравнивается строго `>`): дождаться следующей записи или no-op сервера (раз в 10 с).

   Итог — INFO `итог сверки`: `checked`, `matched`, `defects`, `unverified`, `sampled_out`, `queue`, `schema_defects`, пути `defects_file` и `unverified_file`.
3. «Не проверено» (горячие ключи — `hot`, удалённые коллекции — `drop`) — перепроверить:

   ```sh
   ./bin/mongo-replicator verify --ids "$STATE_DIR"/verify/<dst-db>.<hash>.unverified.json --log-file "$R/verify.log"
   ```

   При дефектах — то же с `defects.json` (подсказка `перепроверьте: …` в логе). Отчёты перепроверки — рядом, `<…>.ids.defects.json`/`<…>.ids.unverified.json`; отчёты основной сверки не затираются.
4. Остановить репликатор (Ctrl+C).

### Критерии готовности

**Готовы**, если всё верно:
- `verify --schema-only` до старта — код `0` или каждое расхождение разобрано и записано;
- финальная сверка `--until-caught-up` — код `0`: `defects` = 0, `schema_defects` = 0;
- перепроверка «не проверено» через `--ids` — код `0`; оставшиеся «не проверено» объяснены в журнале (горячие ключи, `drop`);
- F1–F7 прошли с ожидаемым поведением, после каждого лаг < 10 с и без дефектов;
- F7: лаг < 10 с, RSS без роста, ERROR в логах только ожидаемые (F2, F5);
- E11000, rename, drop, если были, разобраны и записаны.

**Не готовы**, если хоть одно:
- дефект, подтверждённый `--ids`;
- неожиданный выход репликатора с кодом `1` или повторы, которые не прекращаются сами (кроме E11000 из раздела 5);
- лаг не сходится к < 10 с или растёт в F7;
- рост RSS в F7.

При дефектах — разбор до настоящей переливки: `_id` и `ns` из `defects.json` (`src`/`dst` — документы, `reason`), время события — по `jq` в `repl.log`/`verify.log` около ERROR `дефект`.

## 8. Уборка

```sh
docker compose -f deploy/rehearsal/docker-compose.yml down -v   # цель и её тома (данные, keyfile)
rm "$STATE_DIR"/<dst-db>.*.json                                  # файл состояния репликатора (трафик)
rm -r "$STATE_DIR"/verify                                        # позиция, блокировка и отчёты сверки — после переноса итогов в журнал
rm deploy/rehearsal/.env                                         # пароль root стенда
```

Логи `$R/*.log` и журнал сохранить.
