# mongo-replicator

Односторонняя репликация MongoDB через change streams.

Назначение: миграция базы между кластерами MongoDB (в том числе одной версии) — дамп заливается на цель, затем репликатор непрерывно догоняет её до источника, пока не придёт время переключиться. Нужны только права на чтение базы источника и на запись в базу цели: прав на весь кластер, как у `mongosync` или при чтении oplog, не требуется.

Реплицируется одна база источника (`--db`): поток уровня базы, на источнике достаточно прав на чтение этой базы. На цели база может называться иначе (`--dst-db`). Несколько баз — несколько процессов, по одному на базу, в том числе в один целевой кластер (см. [«Несколько процессов»](#несколько-процессов)).

Переносятся DML (`insert`, `update`, `replace`, `delete`) и DDL `create`, `rename`, `createIndexes`, `dropIndexes`. Удаления (`drop` коллекции, `dropDatabase`) не применяются, а останавливают репликатор — решает оператор (см. [«Удаления»](#удаления)).

## Требования

- источник: replica set, MongoDB 6.0+ (нужен `showExpandedEvents` для DDL);
- цель: replica set, MongoDB 8.0; в базу `--dst-db` (и в `_replicator`) пишет только репликатор; другие базы целевого кластера могут использоваться, в том числе другими процессами репликатора;
- на цели уже восстановлен полный дамп источника, а `--start-ts` указывает на момент **до** начала этого дампа и ещё попадает в окно oplog источника;
- права на источнике и цели — см. [«Права»](#права);
- сборка: Go 1.26 (`make build` также выполняет `go mod tidy` и `go mod vendor`); тесты, линтер и `make run` — Docker с compose.

## Запуск

```sh
make build    # bin/mongo-replicator, ревизия из git describe
```

| Опция | Env | По умолчанию | |
|---|---|---|---|
| `--src` | `SRC_URI` | обязательна | URI источника; без пароля в URI пароль запрашивается в терминале (см. [«Пароли»](#пароли)) |
| `--dst` | `DST_URI` | обязательна | URI цели; пароль — так же, как для `--src` |
| `--start-ts` | `START_TS` | `0` | unix-сек, с которых читать поток при отсутствии чекпойнта |
| `--batch` | `BATCH_SIZE` | `1000` | максимум операций в одной пачке записи, `>= 1` |
| `--db` | `DB` | обязательна | база источника (поток уровня базы) |
| `--dst-db` | `DST_DB` | как `--db` | база на цели, куда пишется всё: DML, DDL, обе стороны rename |
| `--apply-drop` | `APPLY_DROP` | — | разрешить `drop` коллекции источника `<db>.<коллекция>` (см. [«После остановки на drop»](#после-остановки-на-drop)); флаг можно повторять, в env — через запятую; флаг заменяет `APPLY_DROP`, а не дополняет |
| `--log-level` | `LOG_LEVEL` | `info` | уровень лога в консоли (stdout): `debug`, `info`, `warn`, `error` (см. [«Логи»](#логи)) |
| `--log-file` | `LOG_FILE` | — | путь к файлу лога: JSON, дозапись; каталог должен существовать |
| `--log-file-level` | `LOG_FILE_LEVEL` | `info` | уровень лога в файле, те же значения; только вместе с `--log-file` |
| `--progress` | `PROGRESS` | `auto` | `tty` — панель статуса в терминале, `plain` — построчный лог, `auto` — панель, если stdout — терминал (см. [«Панель статуса»](#панель-статуса)) |

Без `--db` или с пустым `DB=` — выход с кодом `2`. Уровни лога принимаются только в нижнем регистре и только из списка (`INFO`, `1`, `trace` — выход с кодом `2`); пустые `LOG_LEVEL=` и `LOG_FILE_LEVEL=` — тоже ошибка, пустой `LOG_FILE=` — файла нет. `--log-file-level` без `--log-file` — выход с кодом `2`; `--progress` — только `auto`, `tty`, `plain` (пустое `PROGRESS=` — тоже ошибка, код `2`); ошибка открытия файла лога (нет каталога, нет прав) — тоже. Имена `--db` и `--dst-db` проверяются по правилам MongoDB (без `/\. "$` и NUL, не длиннее 63 байт); служебные базы (`admin`, `config`, `local`, `_replicator`, в любом регистре) указать нельзя. Элементы `--apply-drop` — namespace базы `--db` (`<db>.<коллекция>`, коллекция непустая, имя разбивается по первой точке: `db.a.b` — коллекция `a.b`); пробелы вокруг срезаются, пустой `APPLY_DROP=` — пустой список.

Опции принимаются только с двумя дефисами: `--src`, а не `-src`, как было в первой версии (`-src` разбирается как набор коротких флагов `-s -r -c`).

```sh
./bin/mongo-replicator \
    --src "mongodb://repl@src1:27017,src2:27017/?replicaSet=rs8&authSource=admin" \
    --dst "mongodb://repl@dst1:27017,dst2:27017/?replicaSet=rsdst&authSource=admin" \
    --db urlshrinker \
    --start-ts 1791900000
```

Пароля в URI нет — при старте он будет запрошен в терминале, отдельно для источника и цели (см. [«Пароли»](#пароли)).

Типичный запуск — вручную в `tmux` на часы и дни: в консоли панель статуса и предупреждения над ней, полный JSON-лог — в файле (см. [«Панель статуса»](#панель-статуса), [«Логи»](#логи)):

```sh
./bin/mongo-replicator --src "$SRC_URI" --dst "$DST_URI" --db urlshrinker \
    --log-file /var/log/repl/urlshrinker.log
```

### `--dst-db`

База на цели называется иначе (`urlshrinker` → `urlshrinker_v2`), в том числе копия рядом с оригиналом на том же целевом кластере:

```sh
./bin/mongo-replicator --src "$SRC_URI" --dst "$DST_URI" \
    --db urlshrinker --dst-db urlshrinker_v2 --start-ts 1791900000
```

Дамп на цель заливается сразу под новым именем:

```sh
mongorestore --uri "$DST_URI" --nsFrom 'urlshrinker.*' --nsTo 'urlshrinker_v2.*' dump/
```

На цели пишется только в `--dst-db` (и `_replicator`), база с именем источника там не появляется. Чекпойнт — свой у каждой базы цели, поэтому две копии одной базы на одном целевом кластере (`--dst-db urlshrinker_v2` и `--dst-db urlshrinker_v3`) реплицируются двумя процессами одновременно (см. [«Несколько процессов»](#несколько-процессов)).

URI удобно держать в `cmd/mongo-replicator/.env` (он в `.gitignore`):

```sh
# cmd/mongo-replicator/.env
SRC_URI='mongodb://repl@src1:27017/?replicaSet=rs8&authSource=admin'
DST_URI='mongodb://repl@dst1:27017/?replicaSet=rsdst&authSource=admin'
DB=urlshrinker
```

URI в `.env` — в одинарных кавычках: без них `&` при `. .env` шелл примет за запуск в фоне, и `SRC_URI` останется пустым.

```sh
set -a; . cmd/mongo-replicator/.env; set +a
./bin/mongo-replicator --start-ts 1791900000
```

`--start-ts` нужен только на первом запуске: дальше поток продолжается с чекпойнта на цели, а опция игнорируется.

Чекпойнт — документ базы цели (`_id` = `--dst-db`), он помнит базу источника, для которой записан (поле `db`). Сменить `--db` поверх существующего чекпойнта нельзя — выход с кодом `1` (`ErrDBMismatch`, см. [«Восстановление»](#восстановление)). Другая `--dst-db` — другой документ: без `--start-ts` это выход с кодом `1` (`чекпойнта нет и start-ts не задан`).

Новая полная заливка (например, после выхода с кодом `1` из-за выпадения из oplog): чекпойнт хранится на цели в `_replicator`, в дамп источника он не входит, поэтому перед запуском с новым `--start-ts` его нужно удалить вручную — остановить процесс этой базы и на цели выполнить

```js
db.getSiblingDB('_replicator').checkpoint.deleteOne({_id: "urlshrinker_v2"})   // _id = --dst-db
```

`checkpoint.drop()` не используйте: он сотрёт позиции и накопленный трафик всех процессов этого целевого кластера.

### Пароли

Имя пользователя указывается в URI, пароль — нет. Если в URI есть пользователь, но нет пароля (`mongodb://repl@host/...`, пустой `repl:@host` — то же самое), он запрашивается в терминале без эха: `Пароль repl@src1:27017 (источник): `, затем так же для цели. Запросы независимые: даже при одинаковом пользователе на обоих кластерах пароль спрашивается дважды. Оба запроса — сразу при старте, до подключения, и только после разбора обоих URI: ошибка в `--dst` видна до ввода пароля источника. Пустой ввод или Ctrl+D — выход с кодом `2`, Ctrl+C — выход с кодом `130`, эхо терминала при этом восстанавливается.

URI без пользователя (локальный compose, `make run`) и `authMechanism=MONGODB-X509` / `MONGODB-OIDC` пароля не требуют — запроса нет.

Запрос возможен, только если и stdin, и stderr — терминал (приглашение пишется в stderr): с `2>log` пароль не спрашивается. Запуск без терминала (`nohup`, будущий сервис): передайте URI **с паролем** через окружение — оно не видно в `ps` и не попадает в историю шелла:

```sh
read -rs SRC_URI && export SRC_URI   # вставить mongodb://repl:секрет@src1:27017/?replicaSet=rs8&authSource=admin
read -rs DST_URI && export DST_URI
nohup ./bin/mongo-replicator --db urlshrinker --log-file /var/log/repl/urlshrinker.log \
    >/dev/null 2>>replicator.stderr &
```

stdout не нужен — JSON уже пишется в файл. stderr сохраняется отдельно: туда идут ошибки опций и открытия файла лога, подсказка про пароль без терминала, ошибки записи лога и паника.

Или `.env` с URI с паролем (в одинарных кавычках) и правами `0600` (`chmod 600 cmd/mongo-replicator/.env`). `export SRC_URI=mongodb://repl:секрет@...` прямо в командной строке пароль в историю шелла пишет — используйте `read -rs`. Без терминала и без пароля в URI — выход с кодом `2` с подсказкой про `SRC_URI`/`DST_URI`.

URI с паролем во флаге `--src`/`--dst` работает, но в лог пишется WARN `пароль передан в --src/--dst` (поле `cluster`): командная строка остаётся в истории шелла и видна всем пользователям машины в `ps`. URI с паролем из `SRC_URI`/`DST_URI` — без WARN.

`authMechanism=SCRAM-SHA-1`/`SCRAM-SHA-256` в URI без пароля не поддерживается: драйвер отвергает такой URI до запроса пароля, выход с кодом `2` с подсказкой. Уберите `authMechanism` — механизм по умолчанию сам выберет SCRAM. Для `PLAIN` (LDAP) и `MONGODB-AWS` пароль в терминале не запрашивается: передайте URI с паролем через `SRC_URI`/`DST_URI`. `GSSAPI` (Kerberos) не поддерживается: драйвер собран без тега `gssapi`.

Неверный пароль — выход с кодом `1` при подключении, в логе ERROR `не удалось подключиться` с `hint: проверьте пользователя и пароль`.

### Права

| Источник | Цель |
|---|---|
| `read` на `--db` (`find` + `changeStream`) | `readWrite` на `--dst-db` и на `_replicator` |

`readWrite` включает всё нужное на цели: запись, DDL, `listCollections` (проверка перед `drop`) и `drop` коллекции по `--apply-drop`. Право `dropDatabase` не нужно: `dropDatabase` не применяется.

Чекпойнты на цели — в `_replicator.checkpoint`, по документу на базу цели (`_id` = `--dst-db`); в том же документе — аренда процесса и его накопленный трафик (см. [«Несколько процессов»](#несколько-процессов), [«Трафик»](#трафик)). Права одинаковы для всех процессов: каждому нужен `readWrite` на свою `--dst-db` и на `_replicator`.

`_replicator` на цели заранее создавать не нужно: база, коллекция `checkpoint` и документ базы цели создаются автоматически при захвате аренды на старте, достаточно `readWrite` на `_replicator`.

### Проверка перед запуском

В mongosh под пользователем репликатора. `mongosh "$SRC_URI"` с URI без пароля сам спросит пароль.

Источник — поток по базе открывается (`null` без ошибки — права есть, код 13 — нет):

```js
const cs = db.getSiblingDB("urlshrinker").watch([], {showExpandedEvents: true});
cs.tryNext();
cs.close();
```

Источник — `--start-ts` ещё в окне oplog (`null` без ошибки — в окне, код 286 `ChangeStreamHistoryLost` — выпал, нужна более свежая заливка):

```js
const cs = db.getSiblingDB("urlshrinker").watch([], {startAtOperationTime: Timestamp({t: 1791900000, i: 0})});
cs.tryNext();
cs.close();
```

Цель — запись в `_replicator` и в базу цели (`--dst-db`) с `w: "majority"`:

```js
for (const name of ["_replicator", "urlshrinker_v2"]) {
    const d = db.getSiblingDB(name);
    d.replicator_probe.insertOne({_id: 1}, {writeConcern: {w: "majority"}});
    d.replicator_probe.drop();
}
```

### Локальная проверка

```sh
make docker-volumes   # один раз: тома go-build-cache и go-lint-cache
make run              # mongo-src (8.0, rs8) + mongo-dst (8.0, rsdst) и репликатор с --db test и --start-ts = сейчас
```

Запуск против локальных mongo — только через `make run`: в rs-конфиге члены записаны как `mongo-src`/`mongo-dst`, с хоста эти имена не резолвятся.

`make test-integration` очищает всю `_replicator.checkpoint` на `mongo-dst`, включая чекпойнт базы `test` от `make run`: следующий `make run` начнёт с `--start-ts` = сейчас, а запущенный в это время — выйдет с `ErrLeaseLost`. Чтобы начать с чистого листа — `make down`.

### Разработка

```sh
make test               # юнит-тесты, mongo не нужна
make test-integration   # интеграционные тесты против mongo-src и mongo-dst, строго последовательно (-p 1): тесты очищают общую коллекцию чекпойнтов
make lint               # golangci-lint
make down               # остановить контейнеры и удалить их тома
```

Интеграционные тесты берут кластеры из `IT_SRC_URI`/`IT_DST_URI` (заданы только в сервисе `app` в `docker-compose.yml`), удаляют `_replicator.checkpoint` на цели и базы `it_*` на обоих кластерах. Отдельные переменные нужны, чтобы тесты не ушли на рабочие кластеры из `SRC_URI`/`DST_URI` загруженного `.env`. Запускайте их через `make test-integration`.

## Несколько процессов

Одна база — один процесс. Несколько баз реплицируются в один целевой кластер параллельно — по процессу на базу (`--db`, `--dst-db`), каждый со своим чекпойнтом и своим файлом лога, например в отдельных окнах `tmux`:

```sh
./bin/mongo-replicator --db urlshrinker --log-file /var/log/repl/urlshrinker.log
./bin/mongo-replicator --db billing --log-file /var/log/repl/billing.log
```

Документ чекпойнта базы цели — одновременно **аренда**: при старте процесс записывает в него себя (`owner` — `hostname:pid:<8 случайных hex>`) и срок `lease_until` — время сервера цели + 60 с, затем продлевает аренду каждые 10 с. Продление идёт в своей горутине: долгая операция (сборка индекса `createIndexes` на большой коллекции) его не задерживает. Срок считается по часам сервера цели, часы машин с репликаторами не участвуют. При выходе (сигнал, перманентная ошибка) аренда снимается сразу; не удалось — WARN `аренда не снята: база цели освободится по её истечении`.

- **Второй процесс на ту же базу цели** не стартует: выход с кодом `1`, ERROR `аренда базы цели занята: базу <dst-db> уже реплицирует <owner>, аренда до <время>` (`ErrLeaseHeld`). Если тот процесс упал (`kill -9`, OOM, падение машины) — аренда истечёт сама, новый процесс стартует не позже чем через 60 с.
- **Аренду забрали** — процесс не продлевал её дольше срока (например, машина стояла на паузе) и базу захватил другой: при следующем продлении или сохранении чекпойнта выход с кодом `1`, ERROR `аренда базы цели потеряна` (`ErrLeaseLost`). Проверьте, не запущены ли два репликатора на одну базу.
- **Потеря связи с целью**: продление повторяется каждые 10 с (WARN `продление аренды не удалось, повтор`); если успешного продления нет дольше 40 с (2/3 срока), процесс сам прекращает запись и уходит в обычный повтор (WARN `ошибка репликации, повтор`: `аренда не продлевается и скоро истечёт`) — раньше, чем аренда истечёт и её сможет захватить другой процесс. Когда связь восстановится, процесс захватит аренду заново и продолжит с чекпойнта.

Остаточный риск: операция, уже отправленная на сервер (например, пачка записи), может выполниться на сервере и после остановки процесса на клиенте. Аренда не даёт двум процессам работать одновременно, но такую запоздавшую запись не отменяет.

Все процессы целевого кластера — на цели:

```js
db.getSiblingDB("_replicator").checkpoint.find({}, {token: 0})
```

`_id` — база цели, `db` — база источника, `clusterTime` и `updatedAt` — применённая позиция и время её сохранения, `owner` и `lease_until` — есть, пока процесс работает (или пока не истекла аренда упавшего), `traffic` — накопленный трафик (см. [«Трафик»](#трафик)). Документ без `token` — процесс запущен, но ещё не сохранил позицию. Только работающие сейчас:

```js
db.getSiblingDB("_replicator").checkpoint.find(
    {$expr: {$gt: ["$lease_until", "$$NOW"]}}, {owner: 1, lease_until: 1, clusterTime: 1})
```

## Гарантии

- at-least-once: после сбоя поток продолжается с последнего сохранённого resume token, события после него читаются повторно;
- операции идемпотентны: insert/update/replace применяются как replace-upsert полного документа по `_id`, delete — по `_id`; повторное применение даёт то же итоговое состояние. DDL «уже есть» / «уже нет» при повторе игнорируется;
- чекпойнт хранится на цели (`_replicator.checkpoint`, документ базы цели) и двигается только после успешной записи данных; клиент цели работает с `w:majority`, чтобы чекпойнт не обогнал данные при failover, а сам чекпойнт читается только с primary, даже если в `--dst` задан `readPreference` (устаревший токен с отстающей secondary повторил бы rename поверх применённого состояния);
- после DDL чекпойнт сохраняется сразу, чтобы rename/drop не повторялись после рестарта; при остановке на `drop`/`dropDatabase` всё до удаления уже на цели, а чекпойнт стоит перед удалением;
- любая ошибка, кроме перманентных (см. коды выхода), — повтор через 5 с без выхода. Так переживаются сеть и failover, но так же бесконечно повторяются и постоянные ошибки (цель не приняла документ или DDL): чекпойнт стоит перед проблемным событием, в логе каждые 5 с WARN `ошибка репликации, повтор`. После исправления цели репликация продолжается сама.

Лог пишется в консоль и, с `--log-file`, в файл (см. [«Логи»](#логи)); в терминале консоль по умолчанию заменяет панель статуса (см. [«Панель статуса»](#панель-статуса)). Раз в 10 с — INFO `прогресс` (см. [«Мониторинг лага»](#мониторинг-лага)), раз в минуту — INFO `трафик всех процессов`, при выходе — INFO `трафик` (см. [«Трафик»](#трафик)); применённый DDL — INFO `DDL применён` (`op`, `ns`, `to` — namespace источника; при `--dst-db` ещё `dst` — `ns` на цели, для rename новая коллекция на цели — `<dst-db>.<коллекция из to>`), `drop` по `--apply-drop` — INFO `drop применён по --apply-drop`; пропущенные события — WARN.

Коды выхода:

| Код | Причина |
|---|---|
| `0` | остановка по SIGINT/SIGTERM (незаписанный хвост будет перечитан при следующем запуске); `--help` |
| `1` | точка возобновления выпала из oplog источника (нужна новая полная заливка цели); нет ни чекпойнта, ни `--start-ts`; чекпойнт базы цели записан для другой базы источника (`ErrDBMismatch`); базу цели уже реплицирует другой процесс (`ErrLeaseHeld`) или аренду забрали во время работы (`ErrLeaseLost`, см. [«Несколько процессов»](#несколько-процессов)); на источнике удалена коллекция, которая есть на цели, или база (`*DropError`, см. [«Удаления»](#удаления)); событие другой базы в потоке (`ErrForeignNamespace`, баг); на цели есть база с именем `--dst-db` в другом регистре (сервер отвергает запись, код 13297); поток закрыт событием `invalidate` (`ErrStreamInvalidated`); событие изменения больше 16 МБ (код 10334, см. [«Ограничения»](#ограничения)); кластер недоступен (`Ping` за 10 с) или неверный пароль |
| `2` | ошибка опций, в т.ч. не задана `--db`, некорректное имя базы в `--db`/`--dst-db`, некорректный `--apply-drop`, некорректный уровень лога, `--log-file-level` без `--log-file`, не удалось открыть файл `--log-file` (нет каталога или прав); некорректный URI (в т.ч. ошибка DNS для `mongodb+srv`), нет пароля и нет терминала, пустой ввод или Ctrl+D при запросе пароля — всё до подключения |
| `130` | Ctrl+C или SIGTERM во время запроса пароля |

Перманентные ошибки не повторяются: в лог пишется ERROR с подсказкой оператору, затем выход с кодом `1`.

### Восстановление

- **Выпадение из oplog** — новая полная заливка цели, удаление чекпойнта, запуск с новым `--start-ts` (см. «Запуск»).
- **`ErrDBMismatch`** (`чекпойнт записан для другой пары баз`, в тексте — обе пары): чекпойнт базы `--dst-db` записан для другой базы источника. Если `--db` перепутана — запустите с прежней, чекпойнт подхватится. Если базу источника нужно сменить: остановите процесс, удалите чекпойнт этой базы цели (`deleteOne({_id: "<dst-db>"})`, см. «Запуск»), залейте нужную базу на цель заново и запустите с новыми опциями и новым `--start-ts` до начала дампа.
- **`ErrLeaseHeld`**, **`ErrLeaseLost`** — см. [«Несколько процессов»](#несколько-процессов).
- **Остановка на `drop` коллекции** — см. [«После остановки на drop»](#после-остановки-на-drop).
- **Остановка на `dropDatabase`** (`на источнике удалена база ...`): на цели данные остались, всё до удаления применено. Продолжить старый поток нельзя ни с какими опциями. Когда база на источнике создана заново: удалите чекпойнт, залейте базу на цель и запустите с новым `--start-ts`.
- **`ErrStreamInvalidated`** (`поток инвалидирован`): поток закрыт сервером; в штатном порядке событий до него не доходит — репликатор останавливается раньше, на `dropDatabase`. Восстановление — как после `dropDatabase`.

## Логи

Два приёмника с независимыми уровнями:

- **консоль** (stdout, `--log-level`): если stdout — терминал, цветной текст со временем, а при панели статуса — только WARN и выше над ней (см. [«Панель статуса»](#панель-статуса)); при перенаправлении (`>file`, `| jq`) — JSON;
- **файл** (`--log-file`, `--log-file-level`): всегда JSON, по строке на событие, дозапись (`O_APPEND`); файл создаётся с правами `0640`, каталог — нет.

Поля JSON: `m` — сообщение, `e` — ошибка, `l` — уровень, `t` — время (RFC3339), остальные — по событию.

При старте первой строкой пишется INFO `лог` с настройками приёмников — по ней в файле видна граница запусков. В терминале она выглядит так, в файле — та же строка JSON-ом:

```
2026-10-14T16:00:00+06:00 INF лог console=info/text file=/var/log/repl/urlshrinker.log file_level=info
```

Без `--log-file` — пустой `file` (в терминале `file=`, в JSON `"file":""`), без `file_level`. Строки уровня INFO при старте (`лог`, `revision`) попадают только в приёмники с уровнем `info` и ниже: при `--log-level warn` в консоли их нет.

Уровни раздельные: при разборе проблемы удобно оставить консоль на `info`, а DEBUG писать только в файл:

```sh
./bin/mongo-replicator --db urlshrinker \
    --log-file /var/log/repl/urlshrinker.log --log-file-level debug
```

Запись без буфера: при выходе по сигналу или ошибке ничего не теряется.

Ротация не встроена — внешний `logrotate` с `copytruncate`, например `/etc/logrotate.d/mongo-replicator`:

```
/var/log/repl/*.log {
    daily
    rotate 14
    compress
    delaycompress
    missingok
    notifempty
    copytruncate
}
```

`copytruncate` копирует файл и обрезает исходный, а репликатор продолжает писать в тот же дескриптор; благодаря `O_APPEND` запись идёт с начала обрезанного файла, без «дыры» из нулевых байтов. Строки, записанные между копированием и обрезкой, теряются — обычно это одна-две строки.

## Панель статуса

В терминале внизу экрана — панель, как у `docker build`, обновляется раз в секунду:

```
urlshrinker → urlshrinker_v2 · работает 2ч14м · лаг 1с (применено до 12:01:33)
операции: 1 284 551 всего · 312/с · пачка 12:01:34: 48 (ins 30 · upd 15 · del 3) в links, clicks
DDL: 11:40:02 createIndexes urlshrinker.links (slug_1)
трафик процесса: источник ↓ 3.1 GiB 420 KiB/с ↑ 12 MiB · цель ↓ 40 MiB ↑ 2.9 GiB 390 KiB/с
все процессы (3, активно 2, на 12:01): источник ↓ 12.4 GiB ↑ 307 MiB · цель ↓ 205 MiB ↑ 11.9 GiB
состояние: работает
```

| Строка | |
|---|---|
| заголовок | базы, время работы процесса, лаг и время применённой позиции (`лаг неизвестен` — пока нет чекпойнта или не удался `ping` источника) |
| `операции` | применено с запуска, скорость за последний интервал `прогресс` (10 с), последняя пачка: время, число операций по видам (`ins`, `upd`, `rep`, `del`) и коллекции (до трёх, дальше — «и ещё N») |
| `DDL` | последнее DDL-событие (namespace источника), в том числе пропущенное (с пометкой); нет строки — DDL ещё не было |
| `трафик процесса` | ↓ получено, ↑ отправлено с начала процесса; скорость за последнюю секунду — у основных направлений (источник ↓, цель ↑) |
| `все процессы` | последняя сводка трафика всех процессов цели (раз в минуту): документов, из них с живой арендой, время сводки; нет строки — сводки ещё не было (см. [«Трафик»](#трафик)) |
| `состояние` | `запуск`, `работает`, `повтор N` с ошибкой (жёлтым), `остановлен` (с ошибкой — красным) |

Режим — `--progress` (`PROGRESS`):

- `auto` (по умолчанию) — панель, если stdout — терминал и `TERM` не `dumb`; иначе (`>file`, `| jq`, `nohup`, `TERM=dumb`) — `plain`;
- `tty` — панель;
- `plain` — построчный лог, как описано в [«Логи»](#логи).

С панелью над ней печатаются только WARN и ERROR (и только если `--log-level` их пропускает); INFO (`прогресс`, `DDL применён`, `трафик всех процессов`) в консоль не идёт — его заменяет панель — и пишется только в `--log-file`. Поэтому с панелью запускайте с `--log-file`: без него при старте WARN `полный лог не пишется: добавьте --log-file`. Строки до старта панели (`лог`, `revision`) и итог при выходе (`остановлен по сигналу`, ERROR с подсказкой, `трафик`) печатаются обычным логом: финальная панель остаётся на экране, итог — под ней.

Клавиатуру панель не читает: набранные символы и `^C` терминал отображает поверх панели и может испортить одну-две ячейки, в том числе финальной панели. На работу это не влияет.

## Мониторинг лага

Лог `прогресс` раз в 10 с:

| Поле | Значение |
|---|---|
| `applied` | всего применено операций с запуска |
| `rate` | операций/с за последний интервал |
| `applied_at` | время применённой позиции (RFC3339, UTC) |
| `lag` | лаг строкой (`1m5s`) |
| `lag_sec` | лаг в секундах, число — для алертов по JSON-логу в файле (`--log-file`) |
| `src_in` … `dst_out_bps` | трафик процесса, см. [«Трафик»](#трафик) |

Лаг = текущее время кластера источника (`operationTime` ответа `ping`) минус время **применённой** позиции — токена последнего сохранённого чекпойнта. Чекпойнт двигается только после записи данных на цель с `w:majority`, значит всё до этой позиции уже на цели; прочитанные, но ещё не записанные события в лаг входят. Обе величины — время кластера источника, часы машины репликатора не участвуют.

На простаивающем источнике лаг не растёт: поток отдаёт post-batch resume token, который двигается вместе с oplog источника (периодические no-op, записи в другие базы), и чекпойнт сохраняется с ним.

Лог пишется и пока репликация застряла в повторах (WARN `ошибка репликации, повтор`): позиция стоит, `lag_sec` растёт — алерт по нему срабатывает. Поля `applied_at`, `lag`, `lag_sec` отсутствуют, пока на цели нет чекпойнта; `lag` и `lag_sec` — также если `ping` источника не удался (DEBUG с ошибкой — виден только при `--log-level debug` или `--log-file-level debug`; репликация не прерывается).

`clusterTime` в чекпойнте на цели — то же время применённой позиции, поэтому лаг можно посчитать и без логов. В mongosh, подключённом к источнику:

```js
const dst = new Mongo("mongodb://user:pass@dst1:27017/?replicaSet=rsdst");
const applied = dst.getDB("_replicator").checkpoint.findOne({_id: "urlshrinker_v2"}).clusterTime;   // _id = --dst-db
const now = db.adminCommand({ping: 1}).operationTime;
now.t - applied.t;   // лаг, сек
```

## Трафик

Каждый процесс считает байты, прошедшие через сокеты драйвера к источнику и к цели, — реальный сетевой трафик (уже после TLS и сжатия) для оценки стоимости и нагрузки на сеть.

| | Что |
|---|---|
| считается | поток (`aggregate`, `getMore`) и `updateLookup`; запись на цель; чекпойнт, аренда и сводка; `ping`; heartbeat и RTT-мониторинг драйвера; аутентификация и TLS-рукопожатие |
| не считается | заголовки TCP/IP и ретрансмиты; DNS (в т.ч. SRV для `mongodb+srv`); другие программы на машине; внутренняя репликация кластеров; в чекпойнте — последние ≤10 с перед `kill -9` |

Направления:

| Поле | |
|---|---|
| `src_in` | получено от источника — основной объём: события потока с полными документами; для кластера источника это исходящий (egress) трафик |
| `src_out` | отправлено источнику: запросы |
| `dst_in` | получено от цели: ответы |
| `dst_out` | отправлено на цель — основной объём записи: документы пачек |

Где видно:

- **лог процесса** — с начала процесса, после рестарта счётчики с нуля: в `прогресс` раз в 10 с — `src_in`, `src_out`, `dst_in`, `dst_out` (байты) и `src_in_bps` … `dst_out_bps` (средняя скорость за интервал, байт/с); при выходе — INFO `трафик` с четырьмя суммами и `uptime`;
- **чекпойнт** — по базе цели за все запуски: `traffic.src_in` … `traffic.dst_out` (байты) в документе базы; прирост дописывается при каждом продлении аренды (раз в 10 с) и при выходе;
- **сводка** — раз в минуту (первая — сразу после старта) каждый процесс суммирует `traffic` всех документов `_replicator.checkpoint` на цели: INFO `трафик всех процессов` (`processes` — документов, `active` — из них с живой арендой, `src_in` … `dst_out` — суммы в байтах), в панели — строка `все процессы`. Учитываются только документы с позицией (`token`): процесс, ещё не сохранивший чекпойнт, в сводку не входит; трафик остановленных процессов — входит. Не удалась — WARN `сводка трафика всех процессов не получена`.

Неточности накопления: после `kill -9` или падения машины теряется прирост с последнего продления (≤10 с); если продление дошло до сервера, но ответ потерян (обрыв связи), тот же прирост допишется ещё раз со следующим продлением — один интервал учтётся дважды.

Итог по всем базам в GiB — на цели:

```js
db.getSiblingDB("_replicator").checkpoint.aggregate([
    {$group: {_id: null, src_in: {$sum: "$traffic.src_in"}, src_out: {$sum: "$traffic.src_out"},
              dst_in: {$sum: "$traffic.dst_in"}, dst_out: {$sum: "$traffic.dst_out"}}},
    {$project: {_id: 0, src_in: {$round: [{$divide: ["$src_in", 1073741824]}, 2]},
                src_out: {$round: [{$divide: ["$src_out", 1073741824]}, 2]},
                dst_in: {$round: [{$divide: ["$dst_in", 1073741824]}, 2]},
                dst_out: {$round: [{$divide: ["$dst_out", 1073741824]}, 2]}}}
])
```

По базам — то же с `_id: "$_id"` в `$group`.

Накопленный трафик хранится в документе чекпойнта и удаляется вместе с ним (`deleteOne` перед новой заливкой) — если он нужен, сохраните его до удаления.

Облако насчитает на несколько процентов больше: заголовки TCP/IP, ретрансмиты, DNS и трафик других программ сюда не входят.

## Ограничения

Событие change stream не может быть больше 16 МБ. Репликатор убирает из событий `updateDescription` (ему нужен только `fullDocument`), поэтому обновления документов до ~16 МБ проходят. Если документ так близок к 16 МБ, что не помещается в событие даже без `updateDescription`, сервер отвечает ошибкой 10334, и репликатор выходит с кодом `1`: продолжить можно только новой полной заливкой с `--start-ts` после этого изменения.

Поток читается с `fullDocument: updateLookup`: для `update` на цель пишется текущая версия документа, найденная на источнике в момент чтения события. Отсюда два случая потери данных:

- **(a) updateLookup после rename или drop + recreate.** Если к моменту чтения `update` коллекцию уже переименовали или пересоздали, документ не находится, `fullDocument` пустой и событие пропускается. На цели в новой коллекции остаётся старая версия документа. Воспроизводит `TestLimitationUpdateLookupAfterRename`.
- **(b) rename или drop + recreate в окне `--start-ts` → конец дампа.** Дамп уже содержит итоговую коллекцию `b` целиком, а повтор потока создаёт на цели `a` только из событий окна и переименовывает её в `b` с `dropTarget` — документы `b`, не тронутые в окне, уничтожаются. Воспроизводит `TestLimitationRenameInCatchUpWindow`. Для drop + recreate репликатор останавливается на `drop` (коллекция есть на цели из дампа); потеря происходит, если применить его через `--apply-drop`.

Оба теста помечены `t.Skip`; без него они падают, пока ограничение не устранено. Будущий фикс — включить на источнике `changeStreamPreAndPostImages` и читать поток с `fullDocument: required`: post-image сохраняется в момент изменения и не зависит от последующих rename/drop. До тех пор не выполняйте rename и drop + recreate коллекций в окне дампа и пока репликатор отстаёт.

Rename коллекций внутри реплицируемой базы поддерживается. Перенос коллекций между базами (`renameCollection` из одной базы в другую) не предусмотрен; на 8.0 поток уровня базы видит его так (закреплено `TestIntegrationCrossDBRenameIn` / `TestIntegrationCrossDBRenameOut`):

- перенос **наружу** (`X.a → Y.b`) — приходит только `drop X.a`: репликатор останавливается, как на любом `drop` (см. [«Удаления»](#удаления));
- перенос **внутрь** (`Y.b → X.a`) — приходит как создание временной коллекции, её индексы, вставка всех документов и rename в `X.a` (поверх существующей `X.a` — с `dropTarget`): на цели появляется копия коллекции, репликация продолжается.

### Удаления

Удаления на источнике не предусмотрены: `drop` коллекции, которая есть на цели, перенос коллекции в другую базу (приходит как `drop`) и `dropDatabase` на цели **не применяются** — репликатор выходит с кодом `1` и ERROR с подсказкой. Всё до удаления уже на цели, чекпойнт стоит перед удалением, рестарт с теми же опциями снова останавливается на нём же.

`dropDatabase` ловится уже на первом `drop`: сервер сначала присылает `drop` по каждой коллекции базы (в произвольном порядке), затем `dropDatabase`, затем `invalidate`. Поэтому подсказка в логе будет про коллекцию; если разрешить `drop` всех коллекций, репликатор дойдёт до `dropDatabase` и остановится на нём — `dropDatabase` не разрешается никогда.

Исключения — `drop` применяется или пропускается без остановки:

- временные коллекции самой MongoDB (`tmp.agg_out.<UUID>` от `$out`/`mapReduce`, `tmpXXXXX.renameCollection`, `tmpXXXXX.convertToCapped.*`) — `drop` применяется без остановки (INFO `DDL применён`, без WARN); такой `drop` даёт, например, неудачный `$out`. Имя сверяется с точным форматом, который генерирует MongoDB: пользовательские коллекции с похожими именами (`tmp.backup`, `tmp.agg_out.archive`) под исключение не попадают;
- коллекции, которой нет на цели (view, time-series — их репликатор не переносит, или уже удалённая), — `drop` пропускается с WARN `drop <ns>: на цели такой коллекции нет (view/time-series или уже удалена)`: терять нечего;
- view, который на цели есть (например, восстановлен из заливки), — `drop` применяется без остановки: данных во view нет.

Каждый `$out` (и `mapReduce`) создаёт на цели `tmp.agg_out.*` и пишет WARN `коллекция создана без опций источника, проверьте вручную` — это шум, не ошибка: временная коллекция сразу переименовывается в целевую.

### После остановки на drop

В логе — ERROR с подсказкой `... перезапустите с --apply-drop <ns>`, в поле ошибки — `на источнике удалена коллекция <ns>, на цели не применено`. Если удаление ожидаемое, перезапустите с разрешением:

```sh
./bin/mongo-replicator --apply-drop urlshrinker.links   # или APPLY_DROP=urlshrinker.links
```

- `<ns>` — namespace **источника** (`--db`), даже если `--dst-db` другая: удалена будет `<dst-db>.links`;
- разрешение одноразовое в пределах запуска: после применения и сохранения чекпойнта коллекция вычёркивается, повторный `drop` той же коллекции (например, после пересоздания) снова останавливает репликатор. При рестарте с тем же `--apply-drop` разрешение действует заново — уберите коллекцию из `APPLY_DROP`/команды запуска после применения (об этом напоминает WARN `разрешены drop: ...` при старте);
- сбой между `drop` на цели и сохранением чекпойнта безопасен: при повторе `drop` применится снова, `drop` несуществующей коллекции игнорируется;
- если `drop` (и пересоздание) пришлись на окно `--start-ts` → конец дампа, `--apply-drop` не применяйте: дамп уже содержит пересозданную коллекцию, а `drop` уничтожит её документы, не тронутые в окне (см. [«Ограничения»](#ограничения), (b)). Нужна новая заливка с более поздним `--start-ts`;
- `dropDatabase` так не продолжить — только новая полная заливка (см. [«Восстановление»](#восстановление)).

Уникальные индексы. Идемпотентность replace-upsert по `_id` держится, пока на цели нет уникальных вторичных индексов: при повторе старая версия документа может конфликтовать с более новым состоянием другого документа (E11000), и репликация встаёт в бесконечный повтор (см. «Гарантии»). Устраняется вручную на цели: удалите мешающий документ — последующие события потока его восстановят.

Не поддерживаются (событие пропускается с WARN в логе, переносите вручную):

- `collMod` и прочие изменения опций существующей коллекции;
- views — не создаются;
- опции `create` (capped, validator, collation, timeseries и т.п.) — коллекция создаётся обычной;
- шардирование (`shardCollection`, `refineCollectionShardKey` и т.п.).
